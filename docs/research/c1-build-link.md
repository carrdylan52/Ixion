# Chronicle build and link model, and what a shared-library Ixion build would take

## What this covers

- How Chronicle's PC port is built and linked: `port/CMakeLists.txt`, the Kazarov port CMake it includes, the `port_override.py` list/strip/check pipeline, `port/include/stubs`, `port/src/linknames.cpp`, the PS2 object fixups, the `dc_ps2` / `dc_port` / `dc_host` object libraries, the `darkcloud` executable and the `darkcloud_tests` target.
- Static initialisation, process-wide state, and every place that assumes Chronicle is the main executable, with the work needed to build the whole game as a shared library (DLL or `.so`) that exports only a small C ABI.
- Citation forms: `chronicle:` paths are relative to the Chronicle repo root (master 3bc16763). `kazarov:` paths are at commit a0a5ff8, the pin Chronicle uses; the same files at 3dc38ce (the pin in ChronicleTwo's committed gitlink at its HEAD 8d7d7fc8; 9310c53 is a different commit, not the gitlink) moved to `src/cpp/` and `scripts/build/`, noted where it matters.
- Binary evidence comes from one local Windows build of Chronicle (llvm-mingw, PAL, dated 2026-10-07) inspected read-only with `llvm-nm`, `llvm-objdump` and `llvm-readobj`. That build predates parts of the current tree; see Risks.
- Inference is labelled as such.

## Key facts

- The top-level CMake picks one platform: `PLATFORM` is `PS2` (default) or `PC`; `PC` adds `port/` and enables testing from the top of the tree. (`chronicle:CMakeLists.txt`)
- The port is C++26, clang, position-independent (`CMAKE_POSITION_INDEPENDENT_CODE ON`), and always the PAL release. It includes `tools/kazarov/cmake/KazarovPort.cmake` (`chronicle:port/CMakeLists.txt:22-29`).
- Source sets: `ps2/src/**/*.cpp` gives 136 PS2 units (`PS2_UNITS`); `port/src/**/*.cpp` minus `tests/` gives 118 port units. `PORT_LIB_SOURCES` drops `tests/` and `main.cpp` (`chronicle:port/CMakeLists.txt:40`, `:143`).
- 75 port files contain `PORT_OVERRIDE` (408 occurrences). The macro is an empty marker defined in `kazarov:include/kazarov/port.h`; `PORT` and `PAL` are the defines that make the port's side of PS2 code visible.
- The override pipeline is three `port_override.py` steps (`kazarov:scripts/port_override.py`, docstring lines 1-17; moved to `scripts/build/` at 9310c53):
  - `list port/src -o port_overrides.txt` collects every tagged name (`chronicle:port/CMakeLists.txt:54-62`, the script and the list rule).
  - `strip --overrides ... [--stubs <unit>.hpp] --define=PORT --define=PAL <ps2 unit> <copy>` writes, per ps2 unit, a copy with the tagged definitions removed; the tagged definition keeps only its prototype (`chronicle:port/CMakeLists.txt:79`).
  - `check --overrides ... --stubs port/include/stubs ... -o port_overrides.checked` fails the build if any tagged name matches no ps2/src definition (`PORT_OVERRIDES_CHECKED`, `chronicle:port/CMakeLists.txt:93-97`).
- Each stripped unit is force-included with its stub header when one exists (`set_property(SOURCE ... COMPILE_OPTIONS -include <stub>)`, `chronicle:port/CMakeLists.txt:87-88`). There are 23 stub headers in `chronicle:port/include/stubs/` (including `dun/` and `title/`). They do three jobs: `#define` renames of colliding globals (`edit_in.hpp`, `op_c.hpp`, `op_d.hpp`, `rushmovi.hpp`, `menu_dungeon.hpp`), `asm("...")` labels that give a PS2 `static` a global name the port can reach (`memcard.hpp`, `menu_save.hpp`, `ebattle.hpp`, `editloop3.hpp`, `title/op_d.hpp`), and small prototypes (`frame.hpp`, `cloth.hpp`, `water.hpp`).
- The PS2 link has its own per-unit renames and globalisations in `chronicle:ps2/config/pal/object_fixups.json` (for example `globalize_symbols`, `drop_functions`, `rodata_exports`, `statics`, `symbols`). The port reproduces the parts that matter by hand (`linknames.cpp`, the stub headers).
- `dc_options` (INTERFACE) carries the shared defines (`PORT PAL`), the include roots (`port/include`, `kazarov/include`, `ps2/include`, `ps2/include/sce`), `-include port/include/port.h`, `-fms-extensions`, `-ffunction-sections -fdata-sections`, and `-ffp-contract=off` for identical float rounding (`chronicle:port/CMakeLists.txt:105-115`).
- `dc_ps2` is an OBJECT library over the stripped PS2 units plus the check stamp. It adds `-ftrivial-auto-var-init=zero -fno-strict-return -fno-strict-aliasing -fwrapv` (`chronicle:port/CMakeLists.txt:121-131`).
- `dc_port` is an OBJECT library over the port sources (minus `main.cpp` and tests) plus Kazarov's sce sources for `libvu0 libpad libmc sifdev sifrpc eekernel libcdvd libgraph libdma libpkt` (`chronicle:port/CMakeLists.txt:175-177`). It links SDL3, Vulkan and nlohmann_json PRIVATE.
- `dc_host` is Kazarov's host library: `gfx/`, `audio/`, `platform/` `.cpp` files plus generated SPIR-V headers, as an OBJECT library (`kazarov:cmake/KazarovPort.cmake:34-111`). Its header says host code never sees a game header.
- `dc_link_game(target)` is the one place the executable's objects are gathered: `$<TARGET_OBJECTS:dc_port>`, `dc_host`, `dc_ps2`, then `kz_port_headers`, SDL3, Vulkan and `DC_LINK_OPTIONS` (`chronicle:port/CMakeLists.txt:213-220`).
- `DC_LINK_OPTIONS` (`chronicle:port/CMakeLists.txt:203-211`): Windows is `-fuse-ld=lld -Wl,--gc-sections`; ELF is `-fuse-ld=lld -pie -Wl,-z,separate-code -Wl,--gc-sections` plus `--defsym=draw_rect=draw_rect_store` and `--defsym=WorkBuffer__2=WorkBuffer`; Apple uses `-alias` flags. No target builds `-shared`.
- The executable is `add_executable(darkcloud port/src/main.cpp)` (`chronicle:port/CMakeLists.txt:222`). On Windows it adds `-municode` (`:226`) and the `chronicle.rc` icon. `dc_lang` and `dc_glyphs` copy `lang/`, the two font files and `glyphs/` beside `$<TARGET_FILE_DIR:darkcloud>` (`:236-253`).
- `darkcloud_tests` is `port/src/tests/main.cpp` plus every `*_test.cpp`, linked through `dc_link_game` and `kz_port_tests` (`chronicle:port/src/tests/CMakeLists.txt`). `gtest_discover_tests` runs one process per case, because game state is global. The test `main` calls `GameSetIdentity()` then `RUN_ALL_TESTS()` (`chronicle:port/src/tests/main.cpp:1-20`).
- Entry points: `PORT_OVERRIDE int main(int, const char **, const char **)` is at `chronicle:port/src/main.cpp:471` and calls `Run()` (`:367`). On Windows, `wmain` (`:650`) converts UTF-16 arguments and calls `Run`. The PS2 `main` (`chronicle:ps2/src/main.cpp:436`) is stripped by the override.
- `mwInit` is a no-op override (`chronicle:port/src/runtime.cpp:44-45`). The comment says the host runs the static constructors. `RunGame` also says so (`chronicle:port/src/gameloop.cpp:792`).
- The 2026-10-07 Windows `darkcloud.exe` has 61 `_GLOBAL__sub_I_*` static-init functions (`llvm-nm`), covering about 60 unique basenames. (unverified) Chronicle-owned units include `main.cpp`, `dataset.cpp`, `battlemenu.cpp`, `dataread.cpp`, `edit*.cpp`, `gameloop.cpp` (two units share that basename), `menu_*.cpp`, `mglib.cpp`, `nowload.cpp`, `object*.cpp`, `op_a`..`op_d`, `opening.cpp`, `rushmovi.cpp`, `title.cpp`, `visualvu1.cpp`, `weaponlevelup.cpp`, `fishing.cpp`, `shop.cpp`, `sound.cpp`, `sysmes.cpp`, and the port's own `platform/discord.cpp`. Kazarov units include `audio`, `clock`, `config`, `display`, `displaylist`, `input`, `input_script`, `memory`, `mouse`, `paths`, `pipelines`, `renderer`, `window`, and the sce shims (`libmc`, `sifdev`).
- Named game-level objects with constructors (`chronicle:ps2/src/main.cpp:101,118,136,158`): `CRunScript RunScript`, `static CSaveData save_data`, `CSound CSnd`, `CDebugFont DebugFont`. `chronicle:ps2/src/dataset.cpp:34-37` constructs `VisualData`, `MotionData`, `TextureData`, `WaterData` as `CDataAlloc2<1>(-1)`. `chronicle:ps2/src/battlemenu.cpp:87` constructs `MenuExCashBuffer`. The disassembly of `_GLOBAL__sub_I_main.cpp` calls the `CRunScript`, `CDataAlloc<1,6000>`, `CSaveData` and `CDataAlloc2<1>` constructors in that order (`chronicle:ps2/src/dataalloc.cpp:21`, `dataalloc2_1.cpp:98`).
- Kazarov has its own namespace-scope objects with non-trivial construction: `std::mutex`, `std::filesystem::path`, `std::map` (`audio/soundtrack.cpp:32-35`), `std::vector` pools (`gfx/memory.cpp:33`, `gfx/pipelines.cpp:139`, `platform/arena.cpp:16-19`), the renderer `Context g` (`gfx/renderer.cpp:20`), clock state and hook vectors (`platform/clock.cpp:30-32`), `std::optional` display state (`platform/display.cpp:11-21`), `std::string g_env_prefix` (`platform/settings.cpp:8`), and `std::unordered_set` in `sce/sifdev.cpp:30`.
- PS2 static-init machinery is still in the sources but unused by the port: `__static_init` / `__static_init_end` are bounded in the linker script (`chronicle:ps2/config/pal/SCUS_971.11.lcf:611,633`); `mwInit` and `mwOverlayInit` call `__initialize_cpp_rts` (`chronicle:ps2/src/mathutil.cpp:634-636`, `:657`). The port replaces `mwLoadOverlay` with a stub returning 1 (`chronicle:port/src/runtime.cpp:69-71`).
- Overlays: the port links TITLE and DUN code into the one executable. `LoadOverlay(mode)` only re-runs `TitleOverlayConstruct()` (`chronicle:port/src/runtime.cpp:53-67`), which memsets and placement-new-constructs title objects (`chronicle:port/src/title/title_layout.cpp:38-70`). Retail re-ran each overlay's static initialisers on load.
- Exit and abort sites in the game process:
  - `__assert` calls `std::_Exit(kExitGameAssert)` (`chronicle:port/src/runtime.cpp:13-17`).
  - Metrowerks `exit__2` calls `std::exit` (`chronicle:port/src/runtime.cpp:47-49`).
  - `Exit` in the sce layer calls `std::exit` (`kazarov:port/sce/eekernel.cpp:12-14`). Game code calls it on a GS sync failure (`chronicle:ps2/src/mglib.cpp:487`).
  - Startup fatal paths call `std::exit`: `Usage` and `RequireData` and the input-script check in `chronicle:port/src/main.cpp:102,187,261,381,385`; the extraction failure in `chronicle:port/src/platform/firstrun.cpp:513`; `Fatal` in `kazarov:port/gfx/renderer.cpp:29` and `kazarov:port/platform/window.cpp:24`.
  - Aborts: `NoData` (`chronicle:port/src/dataread.cpp:42,82,87`), texture paths (`chronicle:port/src/texture.cpp:62`, `texture_port.cpp:89`), the arena and memory paths (`kazarov:port/platform/arena.cpp`, `memory.cpp`), the fiber scheduler (`kazarov:port/sce/eekernel_threads.cpp`), and `Ps2Unimplemented` (`kazarov:port/sce/unimplemented.cpp:8`).
- Executable-relative lookups all go through Kazarov's `PathsExecutable()` (`kazarov:port/platform/paths.cpp:102-133`). It returns the host process's image path (`GetModuleFileNameW(nullptr)` on Windows, `/proc/self/exe` on Linux). `Local("data")` and `Local("save")` try the working directory first, then the directory beside the executable (`paths.cpp:49-62`). `PathsDataRoot` and `PathsSaveRoot` cache their answers in process-wide statics (`paths.cpp:188-223`).
- `GameSetIdentity()` runs first in `Run()` (`chronicle:port/src/main.cpp:368`). It calls `PathsConfigure({.app_dir = "chronicle", .env_data = "DC_DATA", .env_save = "DC_SAVE"})`, `SettingsSetEnvPrefix("DC")` and `WindowSetIdentity` with the icon (`chronicle:port/src/identity.cpp`, 15 lines). The `PathsConfig` is process-wide (`paths.cpp` `config`).
- `PathsConsumeArgs` strips `--data` and `--save` from `argv` in place and stores `argv[0]` as the program name (`paths.cpp:135-172`).
- Environment variables are read in many game units: `DC_JUMP`, `DC_GIVE`, `DC_FAST_LOAD`, `DC_INPUT`, `DC_PRESENT_STATS`, `DC_BGM_TEST` (`chronicle:port/src/main.cpp:202-387`), plus tracing and dump hooks in `snd.cpp`, `gameutil_sprite.cpp`, `texture.cpp`, `localize.cpp`.
- Process-global work done in `Run()`: `SDL_SetAppMetadata`, `SDL_SetHint` and `SDL_Init(VIDEO)` (`kazarov:port/platform/window.cpp:62-73`), `SDL_Quit` in `WindowShutdown` (`window.cpp:166`), the Vulkan renderer (`chronicle:port/src/main.cpp:432`), the audio output (`:437`), the Discord client thread (`chronicle:port/src/platform/discord.cpp:393`), clock pump hooks and config change hooks (`main.cpp:441-447`).
- Frame loop: `RunGame` (`chronicle:port/src/gameloop.cpp:791`) is a blocking `for (;;)` (`:864`) with an inner `do { ... } while (result == 0)` (`:916`). It returns `kExitOk` when `FrameBoundaryStop()` is true (`:392`), which is a frame budget or `GameRequestStop()` (`:671`). `RunGame` takes its loop state as locals (`title_ran`, `exist_data`, `data_loaded`, `skip_title`, `result`), so there is no resumable step function.
- The clock is pump-driven. `ClockSyncV` blocks until the next tick and runs the pump hooks (`kazarov:port/platform/clock.hpp`). The tick callback and the idle hook each occupy one slot, "owned by the game side" (same header). Pump hooks are a list. `ClockPump` is not reentrant.
- PS2 threads are fibers on one OS thread: On Windows, `ContextInitMain` calls `ConvertThreadToFiber` (`kazarov:port/sce/eekernel_threads.cpp:50-56`, inside the `_WIN32` branch); on POSIX the fibers are `ucontext` (`:86-97`, the `#else` branch). The scheduler is a function-local static `Sched()` that initialises itself on the first SCE call from any thread (`:146-151`). The comment says no OS thread is ever created by the SCE layer.
- Game-defined libc overrides: `srand` and `rand` are extern "C" definitions of the retail generator (`chronicle:port/src/runtime.cpp:35-42`). On ELF, a default-visibility definition interposes the process's libc `rand`.
- Symbol surface: the 2026-10-07 `darkcloud.exe` has 7015 global defined names (`llvm-nm -g --defined-only`, types T/D/B/R/V/W), including Kazarov's. (unverified: the symbol counts and the 16-name list were not re-derived in this pass) Of those, 2119 names are also defined in the 2026-10-12 ChronicleTwo Windows build. Only 16 of the shared names are plain C game globals: `CSnd`, `SaveData`, `LanguageCode`, `MainCamera`, `WorkBuffer`, `SystemMessage`, `SystemMesBuffer`, `GaijiDataTbl`, `EdEventInfo`, `NameRegistTbl`, `MesAbsDrawOff`, `read_buffer`, `mgRenderInfo`, `mgClearBackFlag`, `mgPickZBuff`, `mgBackColor`. The rest are mostly Kazarov, SDL, libc++ and mangled game names (inference from the name lists, not verified per symbol).
- The 413 external names referenced by `dc_host` objects in that build are libc, libc++, SDL, Vulkan and compiler-runtime names, with no reference to a Chronicle game symbol (checked by name filter, not by full symbol resolution). The Kazarov source at a0a5ff8 calls `SettingsGet()` and `SettingsChange()` from `display.cpp`, `glyphs.cpp`, `input.cpp` and `soundtrack.cpp`, and `SettingsGet` is defined in `chronicle:port/src/platform/config.cpp:568`. The build's objects do not contain those references, so the build differs from the pinned source (see Risks). (unverified: the 413 count and the absence of those references in the objects were not re-checked)
- The `extern "C"` block at `chronicle:port/src/main.cpp:475-645` defines PS2-mangled entry names (`init_all__Fv`, `MenuLoop__Fv`, `EditLoop__Fv`, `func_01DAD980` and others). None of the 2026-10-07 objects reference them, and the final link drops them under `--gc-sections`. `main.cpp` is excluded from `dc_port`, so they exist only in the executable (inference: they are dead, to be confirmed with a fresh build).
- Pointer discipline: `chronicle:docs/port/truncations.md` says `darkcloud` is PIE with all arenas above 4 GiB, so round-trip pointer casts fault at once. `chronicle:docs/DECOUPLING_PLAN.md` still describes `-no-pie`; the current CMake links `-pie`.
- The 2026-10-07 Windows executable imports `SDL3.dll`, `vulkan-1.dll`, `libc++.dll`, `libunwind.dll`, `libwinpthread-1.dll` and UCRT api-set DLLs. It depends on the llvm-mingw runtime DLLs beside it.

## How it works

1. Configure: `cmake -DPLATFORM=PC` with the llvm-mingw clang (Windows) or clang (Linux) and `tools/kazarov` checked out. `KazarovPort.cmake` finds SDL3, Vulkan, glslang and nlohmann_json, fetches or stages the vendor single-file libraries (dr_wav, dr_flac, stb_vorbis, stb_truetype, stb_image), and generates shader headers.
2. Override stamp: `port_override.py list` reads every tagged definition in `port/src`. The stamp re-runs only when a unit or stub header is added or removed.
3. Per-unit copies: each `ps2/src/*.cpp` is stripped of the definitions the port replaces, using its stub header if one exists, into `build/ps2_src/`. The copy is compiled with `dc_options` plus the `-include` stub.
4. Check: `port_override.py check` requires every tagged name to match a definition in ps2/src that the port compiles (the PS2 ifdef state is `PORT`/`PAL`). The stamp is the input to `dc_ps2`.
5. Objects: `dc_ps2`, `dc_port` and `dc_host` compile to object files. `dc_link_game` lists the three object sets as sources of the target, so there is one link line per executable, with no static libraries.
6. Link: the executable is linked with lld, `--gc-sections`, and the alias options. Duplicate names in the three sets would fail the link, so `#define` renames in stubs and the `draw_rect`/`WorkBuffer__2` aliases exist to keep them apart.
7. Run: `main` calls `Run` (window, renderer, audio, clock hooks), then `RunGame` (InitCDFile, MGInit, the static game state, `init_now_loading`), then the mode loop. Frame timing is driven by the clock pump inside `ClockSyncV`.
8. Tests: the same objects, minus `main.cpp`, are linked with gtest. Each case runs in its own process.

## Ixion hooks

These are the integration points in the current Chronicle tree, with what Ixion could do at each.

- `chronicle:port/src/main.cpp:471` (`main`) and `:650` (`wmain`): the only process entries. Ixion's shared library would not define these. Move the body of `Run` (`:367-470`) into a library file that exports `ixion_init`, `ixion_step` and `ixion_shutdown` (C signatures, a config struct of plain-old-data, and error codes instead of `std::exit`).
- `chronicle:port/src/gameloop.cpp:791-973` (`RunGame`): the blocking loop. For Ixion, turn the loop's locals (`title_ran`, `exist_data`, `data_loaded`, `skip_title`, `result`) into file or context state, so one pass of the `do ... while` becomes `ixion_step()`. Keep `FrameBoundaryStop` and `GameRequestStop` as the stop path.
- `chronicle:port/src/runtime.cpp:13-17` (`__assert`), `:47-49` (`exit__2`), and the `std::exit` and `abort` sites listed in Key facts: route through a host-supplied fatal callback, or return an error from `ixion_step`. A host process should not die on a game assert.
- `chronicle:port/src/identity.cpp` (`GameSetIdentity`): parameterise the app directory, the environment variable names and the window identity, so two games do not overwrite each other's `PathsConfig`.
- `kazarov:port/platform/paths.cpp:102` (`PathsExecutable`) and `:188-223` (roots): the existing `PathsSetDataRoot` and `PathsSetSaveRoot` (paths.hpp) let Ixion set the data and save roots explicitly from its API, so the DLL need not find its own file. Also copy or locate `lang/`, `glyphs/` and the fonts (`chronicle:port/CMakeLists.txt:236-253`) relative to the library's directory, not the host's.
- `kazarov:port/platform/clock.hpp` (tick callback and idle hook as single slots; pump hooks as a list): Ixion needs one clock per game, or a multiplexer. Ixion's stepper could replace the pump with an explicit `ClockPump()` call per host frame.
- `chronicle:port/src/platform/discord.cpp:393` and the window/SDL setup (`kazarov:port/platform/window.cpp:62-73, 166`): `SDL_Quit` tears down every subsystem for the whole process. Ixion should own SDL init and shutdown once, and the game DLL should not call `SDL_Quit`.
- `kazarov:port/sce/eekernel_threads.cpp:50-56, 146-152`: the scheduler converts the first calling thread into a fiber. Ixion should call `ixion_step` (and init) only from one thread, documented in the API, and should bind that thread explicitly.
- `chronicle:port/src/runtime.cpp:35-42` (`rand`/`srand`): keep them hidden in the library, so the host's libc is not interposed.
- `chronicle:port/src/linknames.cpp:148-153` (the `.globl` asm label and `[[gnu::constructor]] CopyEditGaijiTable`): the `.globl` makes a default-visibility symbol that a version script must hide. The constructor is a second static initialiser that depends on `GaijiDataTbl`.
- `chronicle:port/src/linknames.cpp:32-33` (`#pragma comment(linker, "/alternatename:...")`): COFF aliases. They work in a DLL but the same names must exist in each game's DLL.
- `chronicle:port/CMakeLists.txt:203-220` (`DC_LINK_OPTIONS`, `dc_link_game`): add a `SHARED` (`-shared` on ELF, `-shared` on lld-mingw) variant that skips `main.cpp`, drops `-pie`, and adds the version script or export list.
- `chronicle:port/src/tests/main.cpp`: a test-only harness that calls `GameSetIdentity()` and `RUN_ALL_TESTS()`. It shows that the game can be driven in-process without `main`, which is the model for a loader test.

Build plan for a shared-library Ixion, in order (effort is inference):

1. Add a `ixion_dc1` target (SHARED) built from the same three object sets as `dc_link_game`, minus `port/src/main.cpp`. Add `-fvisibility=hidden -fvisibility-inlines-hidden` to `dc_options` for that target only. This needs its own object libraries, because the object sets are shared with the executable.
2. Export only `ixion_*`. On ELF, use a version script with `global: ixion_*; local: *;`. On Windows, mark the C API `__declspec(dllexport)` and add `-Wl,--exclude-all-symbols` (inference: lld's MinGW mode auto-exports when no `dllexport` is present; check with `llvm-objdump -p` on the DLL).
3. Make the `.globl` asm label in `linknames.cpp:148` hidden (`.hidden`), or rely on the version script.
4. Refactor `Run` and `RunGame` into init, step and shutdown functions. This is the largest change: the loop body is about 60 lines, with the state locals listed above.
5. Replace each exit, abort and `_Exit` with a return code or a fatal callback (the list in Key facts).
6. Provide a `ixion_set_paths` (or pass a config struct) so the DLL never calls `PathsExecutable` for its data.
7. Verify static initialisation on Windows: confirm the DLL's entry point reaches the `__xc_a`..`__xc_z` range (the executable has these symbols; the DLL needs them too). If it does not, call an explicit initialiser. On ELF, `.init_array` runs at `dlopen`.
8. Deploy `SDL3.dll`, `vulkan-1.dll` and the llvm-mingw runtime DLLs beside the host, as the executable does.

## Risks and blockers

- Static-initialiser order. The PS2 ran `__static_init` tables in link order, and overlays ran their own on load. The port runs every constructor at process start in object-link order (`dc_port`, then `dc_host`, then `dc_ps2`). Cross-unit dependencies between namespace-scope objects are not ordered by the language (inference: none found in this pass, but none were checked exhaustively). A DLL changes the order.
- Overlay constructors now run at startup rather than on overlay load. `TitleOverlayConstruct` re-builds some title objects by hand, which may diverge from what a construction at load would do (inference).
- Every game-side exit or abort kills the host process. This includes `__assert`, `exit__2`, the sce `Exit`, `Fatal` in the renderer and window, and `NoData` (abort).
- Process-wide state is singular: `PathsConfig` and the cached data/save roots, `SettingsSetEnvPrefix`, the clock tick callback and idle hook (one slot each), the `g_hooks` and `ConfigAddChangeHook` lists, the SDL hints and metadata, `SDL_Quit`, the Vulkan renderer `gfx::g`, the audio mixer, and the Discord thread. Two games in one process need separate copies of all of these, or one game at a time with state handover (inference).
- Two games in one process: 16 plain C game globals (`CSnd`, `SaveData`, `LanguageCode`, `MainCamera`, `WorkBuffer` and others) and many mangled names are defined in both builds. Hidden symbols in separate DLLs avoid a link collision, but a single link of both games would fail on these names (see the symbol overlap in Key facts).
- The fiber scheduler binds to the first thread that makes an SCE call. Calling `ConvertThreadToFiber` twice on one thread fails and aborts (Windows only, `eekernel_threads.cpp:52-55`). Two game DLLs on one thread each carry their own scheduler copy (inference).
- ELF default-visibility symbols interpose the host. The `rand`/`srand` overrides and the weak literal definitions in `linknames.cpp` (`PORT_LINK_NAME`, `__attribute__((weak))`) would override the host's copies if exported.
- Pointer size discipline: the game casts pointers through `int` in about seventy units. A DLL image must still map above 4 GiB, as the executable's does. Windows ASLR usually satisfies this, but it is unverified for a DLL (inference), and the build's `.reloc` section shows the executable is relocatable.
- The 2026-10-07 build directory predates the current tree in places. `kazarov:port/platform/*` at a0a5ff8 calls `SettingsGet`, but that build's `dc_host` objects reference no such symbol. Re-running the build before trusting the symbol facts is required.
- The `main.cpp` extern "C" shims are dead in the 2026-10-07 build, but this is inferred from one build (see Key facts).
- Kazarov pins differ between the two games: Chronicle at a0a5ff8 (`port/`, `scripts/port_override.py`) and ChronicleTwo at 3dc38ce (`src/cpp/`, `scripts/build/`, verified). A shared Kazarov for Ixion must pick one layout, or the two game builds must each keep their own copy.
- Apple builds are in `CMakePresets.json`, but the project's workspace rules rule out Apple software for this effort, so no macOS link model is proposed here.
- Chronicle's own tests and the `dcdata` tool are built from the same tree; a DLL target needs its own test strategy.

## Open questions

- Does lld-mingw auto-export when the DLL has no `dllexport`? (Check with a small test DLL.)
- Does the DLL entry (`DllMainCRTStartup` from the llvm-mingw CRT) run the `__xc_*` initialisers for a `-shared` link of this code? (Check with `llvm-objdump` on a test DLL.)
- Are the `extern "C"` shims in `port/src/main.cpp:475-645` referenced by any object in a fresh build? (Check with `llvm-nm -u` on the new objects.)
- Which game-level globals depend on the static-initialiser order? A ctor-order audit of the 61 init functions would answer this.
- Can `RunGame`'s loop state move to a context struct without changing frame timing? The loop and `ClockSyncV` interact (`MGEndFrame` pumps the clock).
- Can the scheduler, clock and SDL be made per-instance so that two game DLLs can coexist in one process? If not, Ixion's design must run one game at a time and hand state over (save bytes, map and party state) through the C ABI.
- Should the shared library be Kazarov-based on both sides? That decides whether `kazarov:port/platform/*` is shared or duplicated.
