# Chronicle memory model and global state

## What this covers

How the Dark Cloud (DC1) PC port keeps the PS2's memory layout: the quadword arenas (`CDataAlloc2`, `GlobalDataBuffer`, `WorkBuffer`), the arena host layer in Kazarov, the scratchpad and VU-memory stand-ins, the pointer-truncation work recorded in `docs/port/truncations.md`, and the inventory of static and global state that a second game sharing the process would have to save, reset or isolate. Footprints are estimates from source arithmetic and from the section and symbol tables of an existing Windows build; they are labelled as such. Citations use `chronicle:` for the DC1 repo, `chronicletwo:` for DC2, and `kazarov:` for the shared host (current main, commit 9310c53; the Chronicle pin a0a5ff8 has the same arena files under `port/platform/`, and `arena.hpp`, `arena.cpp` and `memory.hpp` are byte-identical across the two layouts) (unverified: the Chronicle clone checked does not contain the a0a5ff8 pin).

## Key facts

- The PS2 heap is one 27,040,000-byte block. `CDataAlloc<1, 1690000>` is `GlobalDataBuffer`, 1,690,000 quadwords; its symbol size is 0x19C9910 bytes. PAL address 0x002B2800 (chronicle:ps2/config/pal/main.symbols.txt:8804). chronicle:ps2/src/dataset.cpp:41
- Every other PS2 data region is a sub-arena carved from that block with `Alloc64` (64-byte aligned). Carve sizes are hard-coded in quadwords at the call sites, for example `SetDataBuffer(&MapModelBuffer, 0xA7F80)` and `SetPacketReadBuffer(0x9344, 0x445C0)` (chronicle:ps2/src/dun/gameloop.cpp:1443-1464).
- Port arenas are no longer slices of `GlobalDataBuffer`. Each arena is its own host block, keyed by the address of the arena object (`ArenaBlock(arena, quads * 16 * kArenaHeadroom)`), and every arena gets 4x the retail quadword count (chronicle:port/src/dataset.cpp:12-18). `kArenaHeadroom = 4` is defined in kazarov:include/platform/arena.hpp:11, with the reason given in the comment above it: the game sizes structures with host `sizeof`, which grows with 8-byte pointers.
- `GlobalDataBuffer`'s own 27 MB member is still compiled into the image, but the port's `GlobalBlock()` (4x size) backs its `Alloc`, and nothing in the game's own call graph reaches it. Only the tests in chronicle:port/src/tests/platform_arena_test.cpp exercise `GlobalDataBuffer.Alloc64`. Inference from a grep of call sites (chronicle:port/src/dataalloc2_1.cpp:14-17, 91-112).
- The retail PS2 layout is 32 MiB of RAM. `GlobalDataBuffer` alone is 80% of it. The PAL overlay origin is 0x01DC4000 and the overlay's .bss range runs to 0x01F06B00 (about 1.3 MB above the origin), so the whole 32 MiB address map is nearly full (chronicle:ps2/config/pal/main.symbols.txt:8804; chronicle:scripts/build/region.py, `overlay_origin` and the PAL `.bss` range). NTSC uses 0x01DABD00.
- The PS2 dungeon load fills almost all of `GlobalDataBuffer`. Summing the quadword arguments of the dungeon load (chronicle:ps2/src/dun/gameloop.cpp:1443-1464) plus the `InitializeDataBuffer` carves (10 + 25000 + 25000) gives 1,623,716 quadwords, 96.1% of 1,690,000. Arithmetic over source values, not measured.
- Host arena reservation is 4x the PS2 quadwords. Startup (`BufferAllClear`, chronicle:port/src/dataset.cpp:54-67) reserves 1,444,096 quadwords, about 92 MB, plus a 1.5 MB lead for the read buffer. The dungeon's distinct arena keys, each at its largest carve, total about 2.82 M quadwords, about 181 MB. The editor's `DataBuffer__2` alone is 1,216,000 quadwords, about 78 MB. Upper bounds on reserved address space, not resident memory.
- Arenas are mapped with `MEM_RESERVE | MEM_COMMIT` on Windows and zeroed by `madvise(MADV_DONTNEED)` on Linux or by decommit and recommit on Windows (kazarov:src/cpp/platform/memory.cpp, `ArenaMemoryMap` and `ArenaMemoryZero`). On Windows the commit charge therefore covers the whole reservation at map time, not only the pages touched. Inference from the code; not measured.
- `ArenaBlock` keeps a replaced block alive. If an owner asks for more than its current capacity, the old block is zeroed, pushed to `g_retired`, and never unmapped; a stale pointer into it reads zeros (kazarov:src/cpp/platform/arena.cpp:50-65). Retired blocks count toward `ArenaContains`.
- `ArenaClearAll()` zeroes every live block in the process, and `BufferAllClear` and `InitializeDataBuffer` both call it (kazarov:src/cpp/platform/arena.cpp, `ArenaClearAll`; chronicle:port/src/dataset.cpp:37, 55).
- Two arenas are placed on purpose. `read_buffer` is given a 0x180000-byte lead (`kReadBufferLead`, chronicle:port/src/dataset.cpp:12, 30-31) because the editor computes `EdMenuBuffer.base = read_buffer - 0x180000` (chronicle:ps2/src/editloop.cpp:514). `BtCashBuffer.base` is set to `BtScriptWorkBuffer.base` as an alias (chronicle:ps2/src/dun/gameloop.cpp:4477). The editor carves its NPC buffer at a hard-coded offset inside `DataBuffer__2` (chronicle:ps2/src/editloop.cpp:762, `+ 0xCF8500`).
- The port keeps the `CDataAlloc2` placement semantics but enlarges objects placed in arenas. `operator new(size, block)` grows the arena's most recent run to the host size of the object (chronicle:port/src/dataalloc2_1.cpp:35-61), using a file-scope `g_last_run` record.
- The PS2 scratchpad (0x70000000) is used as a pointer in two retail functions: `CCloth::Step` (chronicle:ps2/src/cloth.cpp:170, inside `#ifndef PORT` at lines 87-455) and `CVisualShadow` (chronicle:ps2/src/visualshadow.cpp:278, replaced by PORT_OVERRIDE at chronicle:port/src/visualshadow.cpp:306-354). The same value appears as a register word in the DMA setup table `My_DrawEnv` (chronicle:ps2/src/vudata.cpp:27), which is data, not a pointer. The port solves cloth in stack arrays of about 4.5 KB (chronicle:port/src/cloth_step.cpp:46-52). No scratchpad region is mapped.
- VU microprograms are data only. `Vu_prog0`, `Vu_prog0f`, `Vu_shadow` and friends live in `.vutext` (42,944 bytes in the PC build; chronicle:ps2/src/vutext.cpp:9). Port code reads them for constants and tables, but no VU code is interpreted. `MGInitVif1Packet` is a no-op in the port (chronicle:port/src/dataset.cpp:69), and geometry reaches the GPU through a Draw3D record registry, not VIF packets (chronicle:port/src/visualvu1.cpp:21-41, 397-430).
- Draw3D records are keyed by arena address. `Draw3DRegisterVisual` writes a tag word into the arena block (`block[8] = 0x44334443`, "CD3D") and keeps two `unordered_map`s, one transient and one lasting. `Draw3DSweepVisuals` drops entries whose tag has gone (chronicle:port/src/visualvu1.cpp:21-41, 410-430).
- The texture registry is a process-wide table of 16,384 entries, one per 14-bit key (TBP0 and CBP share the space). Keys 0 and 0xFFF are the frame targets and are never handed out, and keys below 0x20 are reserved (`kFirstKey`) (chronicle:port/src/texture_port.hpp, registry comment; chronicle:port/src/texture_port.cpp:15, 47-60). `PortReleaseOwner(Manager)` releases every entry owned by any `CTextureManager` (chronicle:port/src/texture_port.cpp:410-416). Each manager's `Initialize` registers a render target named "work" (chronicle:port/src/texture.cpp:379-406).
- `CTextureManager`'s constructor calls `Initialize(16352)` (chronicle:ps2/include/texture.hpp:106), so the manager's setup runs during static initialisation. The port comments that this order is not controlled (chronicle:port/src/texture_port.cpp:50-53).
- GS state is a set of globals in `mglib.cpp`: `mgTEX1Env`, `mgPixelTest`, `mgZBuffer`, `mgAlpha`, `mgTexa`, `mgDBuff`, `mgRenderInfo`, `mgWindowRectStore`, `mgPickZBuff[16]`, `GiftagAD`, `VSyncField__2`, `Vif1Packet`, `DmaCH8` (chronicle:ps2/src/mglib.cpp:31-80). `mgTopVRAM` is set to 0x1E00 for PAL (mglib.cpp:143). The texture code's VRAM size is 16352 in 64-word units (chronicle:ps2/src/texture.cpp:907; chronicle:ps2/src/main.cpp:1067), about 4 MiB, the GS VRAM size.
- Random numbers come from a single process-wide state. The port overrides `rand` and `srand` with `g_rand_state`, which the game's own sequence depends on (chronicle:port/src/runtime.cpp:25-43). The comment says a fire reseeds the generator every tick, so the exact sequence matters.
- The overlay loader's state is one `static Overlay loaded` in the port's `LoadOverlay` (chronicle:port/src/runtime.cpp:54-66). On retail, TITLE.BIN and DUN.BIN both load at `_overlay_group_addresses[1]` (chronicle:ps2/src/main.cpp:281-296), so the two overlays share PS2 address space and only one is resident at a time. The port keeps both resident and re-runs the title overlay's constructors whenever the title overlay becomes current again (chronicle:port/src/title/title_layout.cpp:38-57; chronicle:port/src/runtime.cpp:54-66).
- The save is one `CSaveData` of 78,272 bytes (chronicle:ps2/include/savedata.hpp:501). Its `map_no` sits at offset 0x1C8 (`kSaveMapNoOffset`, chronicle:port/src/gameloop.cpp:69), and `RunGame` writes it through a raw offset (chronicle:port/src/gameloop.cpp:913). The port's live copy is `g_save_data` (chronicle:port/src/gameloop.cpp:217), and `SaveData` points at it (gameloop.cpp:818). The ps2 translation unit still defines its own `static CSaveData save_data` (chronicle:ps2/src/main.cpp:118), about 78 KB that the port's `main()` override does not reference (inference).
- The PC build's `.data` section is 33,455,304 bytes (`VirtualSize`, `darkcloud.exe` from the Oct 7 build, read with llvm-readobj). `.text` is 2,063,894 bytes. `.vutext` is 42,944 bytes (same build). Most of the `.data` section is `GlobalDataBuffer`. (unverified: the binary was not re-read in this check.)
- Excluding `GlobalDataBuffer`, the PC build's static and global data is about 6.5 MB across roughly 2,275 `.data` and `.bss` symbols. Sizes are estimates from address gaps, since COFF symbols carry no size. The largest: `g_dance_pack` (2 x 0x130000 = 2,490,368 bytes, chronicle:port/src/title/op_b.cpp:283), `MainMonstorUnit` (~497 KB), `ShotEffect` and `MasekiEffect` (~265 KB each), `Chara__3` (~134 KB, 23 slots), `SystemMesBuffer` (96,016 bytes, chronicle:ps2/src/main.cpp:107), two `CSaveData` copies (78,272 each), `MainDungeonMap` and `UraDungeonMap` (~77 KB each), and `mes_data` (48 KB, chronicle:ps2/src/sysmes.cpp:110).
- PC struct sizes run 10-30% above their PS2 `STATIC_ASSERT`s for pointer-heavy classes. `CCharacter` is 0x11B0 bytes on PS2 (chronicle:ps2/include/character.hpp:570) and roughly 5.8 KB per slot in the PC build (inference from the symbol gap). `CMonstorUnit` is 0x60750 on PS2 (chronicle:ps2/include/monstorunit.hpp:535) and about 497 KB for `MainMonstorUnit` in the PC build. `CDungeonMap` is 0x10B10 on PS2 (chronicle:ps2/include/dungeonmap.hpp:666) and about 77 KB in the PC build.
- Global and file-scope declarations number roughly 1,400 at column zero in `ps2/src` (66 files), 1,074 `extern` declarations across `ps2/include`, about 280 indented function-local statics in `ps2/src`, about 163 in `port/src`, and about 126 distinct `g_*` singletons across roughly 45 files in `port/src`. Counts come from ripgrep patterns, so they include some false positives.
- The DC2 repo has the same arena host (chronicletwo:port/src/arena_root.cpp:13-14, `ArenaBlock` keyed by a caller-supplied key) but a different PS2-side allocator, `mgCMemory` with `stSetBuffer` (chronicletwo:ps2/include/mg_memory.hpp:229). DC2's `CSaveData` is 0x65930 (416,048) bytes (chronicletwo:ps2/include/savedata.hpp:504).
- DC1 and DC2 both define C++ classes with the same names but different layouts: `CGamePad` (DC1 0x468, chronicle:ps2/include/gamepad.hpp:451; DC2 0x478, chronicletwo:ps2/include/gamepad.hpp:676), `CSound`, `CRunScript`, `ClsMes`, and `CSaveData`. The two decompilations also share a flat C symbol space: `WorkBuffer__2` is aliased to `WorkBuffer` by a COFF `alternatename` pragma (chronicle:port/src/linknames.cpp:32-33). A combined executable would need namespaces or separate link units to avoid collisions.
- The truncation work (chronicle:docs/port/truncations.md, generated by `scripts/port/truncations.py`) classifies about 149 sites. Round trips: 13 total, 0 that run in retail or the port (12 replaced, 1 dead). Resolved: 72, of which 16 are port code. Escapes: 42, one live (chronicle:port/src/editloop_parts.cpp:58). Low-bits: 22, of which 9 run in retail or port. Zero round trips that run is what lets arenas sit above 4 GiB without faults.
- The one pattern the port relies on for pointers stored in 32-bit fields is `PortImagePointer`, which widens a truncated value to the nearest address with the same low 32 bits to the executable image (kazarov:include/platform/arena.hpp, `WidenNear` and `PortImagePointer`). It is used only for `CCharacter::wind`, which is always an image global (chronicle:port/src/character.cpp:1-38).
- The arena layer's over-4-GiB check is debug-only (`CheckSomeBlockHigh` and `ArenaRequireOneAbove4GiB` in kazarov:src/cpp/platform/arena.cpp:37-45 and 80-88, both under `#ifndef NDEBUG`).
- Host identity is process-global. `GameSetIdentity` sets the environment prefix "DC", the app directory "chronicle", and the window title (chronicle:port/src/identity.cpp:6-12), each stored in a single kazarov global (kazarov:src/cpp/platform/settings.cpp:8; paths.cpp:92; window.cpp:16-20).
- The game runs on one thread. The only threads in the port are in the Discord and first-run modules (chronicle:port/src/platform/discord.cpp, firstrun.cpp).

## How it works

**Layers.** Three layers hold memory. (1) Retail arenas: `CDataAlloc2<Kind>` objects with a base, a buffer, a used count and a limit (chronicle:ps2/include/dataalloc.hpp:22-30; the port's copy is 24 bytes on a 64-bit host, against 16 on PS2). (2) Host arenas: `ArenaBlock(owner, bytes, lead)` returns a zeroed, 64-byte aligned block that stays with its owner key while it fits, followed by an inaccessible guard page (kazarov:src/cpp/platform/memory.cpp, `ArenaMemoryMap`). (3) The embedded `CDataAlloc<1, 6000>` for `SystemMesBuffer`, which keeps its storage inside the object (chronicle:port/src/dataalloc2_1.cpp:119-127), and `CDataAlloc<1, 1690000>` for `GlobalDataBuffer`, whose embedded storage is unused in the port.

**Lifetime.** Scene loads follow a fixed pattern: `InitializeDataBuffer` (or `BufferAllClear` at startup) clears every host block and carves the long-lived arenas, then each scene calls `SetDataBuffer` for its own arenas. A re-carve with the same owner key reuses the block if it is big enough, and otherwise retires it. Pointers into an arena remain valid for the life of its block, which is why retired blocks are kept mapped.

**Read buffer and packets.** `SetPacketReadBuffer` carves the read buffer (with lead), two packet buffers that the port never fills, and the 2048-quadword `workbuffer`, then points `WorkBuffer` at it. `WorkBuffer__2` is an alias for the same pointer variable (chronicle:port/src/linknames.cpp:32-33). Scripts and effects reset `WorkBuffer__2->used = 0` and allocate polygon lists from it (for example chronicle:ps2/src/ebattle.cpp:1715-1716).

**Overlays.** `LoadOverlay` on retail maps the TITLE or DUN overlay to group 1. The port ignores the file and tracks which overlay is current in a single static, constructing the title's host-sized objects with `memset` followed by placement new (chronicle:port/src/title/title_layout.cpp:33-57).

**Truncation handling.** The sites are classified in `docs/port/truncations.md`. Where a retail function narrows a pointer and casts it back, the port replaces the function (a `PORT_OVERRIDE` definition in `port/src`) and keeps the pointer whole. Where the value is an image global, `PortImagePointer` recovers it. The only remaining live escape is at chronicle:port/src/editloop_parts.cpp:58.

**Static and global state.** Globals come in four kinds:
- Constructed globals run host constructors before `main`. The port's `mwInit` is a no-op (chronicle:port/src/runtime.cpp, `mwInit`), so construction order across translation units is unspecified.
- Plain globals and `static` arrays sit in `.data` or `.bss`.
- Function-local statics (for example `static int flag` in `LoadMDSFile`, chronicle:ps2/src/dataset.cpp:351) keep state across calls.
- `g_*` singletons in `port/src` are host-side state (renderer, audio, input, texture registry, Draw3D maps, localization, config).

## Ixion hooks

- **Arena domains (kazarov, `ArenaBlock` and `ArenaClearAll`).** Give each game its own owner namespace, or key blocks by (game, owner). `ArenaClearAll` should take a domain, so that one game's `BufferAllClear` cannot zero the other's live arenas (kazarov:src/cpp/platform/arena.cpp, `ArenaClearAll`).
- **Startup and scene reset (chronicle:port/src/dataset.cpp:36-69).** `InitializeDataBuffer` and `BufferAllClear` should be called per game, each clearing only its own domain.
- **Session object for RunGame (chronicle:port/src/gameloop.cpp:791-973).** `RunGame` owns the mode and map globals (`mode`, `MapNo`, `OldMapNo`, `LocalMapNo`, `NextMapNo`, `StartEventNo`, `GameClearFlag`, `main_select_menu_no`, `PolyCount`, `DebugMode`, `LanguageCode`; chronicle:ps2/src/main.cpp:119-164, 240-256; chronicle:ps2/src/mainselect.cpp:9-15). A world switch needs to save and restore these as a unit, along with `SaveData` (gameloop.cpp:818) and `g_save_data` (gameloop.cpp:217).
- **Per-world save (chronicle:port/src/save_slots.hpp; chronicle:port/src/platform/save_state.hpp).** Each DC1 save is `<save root>/saves/N/save.dat`, a 78,272-byte image, plus a global `state.json`. A combined save should store the DC1 image and the DC2 image side by side in one folder.
- **RNG (chronicle:port/src/runtime.cpp:25-43).** Save and restore `g_rand_state` at each world switch, or give each game its own state.
- **Overlay state (chronicle:port/src/runtime.cpp:54-66).** Make `loaded` per game, and let a world switch decide which constructors to run.
- **Texture registry (chronicle:port/src/texture_port.cpp:47-60, 410-416).** Either give each game its own registry or key entries by (game, TBP). `PortReleaseOwner(Manager)` should release only the current game's manager entries, and the "work" target name should be unique per game (chronicle:port/src/texture.cpp:379-406).
- **Draw3D maps (chronicle:port/src/visualvu1.cpp:21-41, 397-430).** Keyed by arena address, so they follow the arena domain. `Draw3DSweepVisuals` runs at `MGBeginFrame`, which is also the point to clear a world's transient records.
- **GS state (chronicle:ps2/src/mglib.cpp:31-80; `MGSetRenderInfo` in RunGame).** Reinitialise GS state for each world. `RunGame` already calls `MGSetRenderInfo(800.0f, 10.0f, 65535.0f)` on every mode change (chronicle:port/src/gameloop.cpp, `RunGame`).
- **Sound (chronicle:port/src/sound.cpp:31-53).** `midi_state`, `g_slot_banks`, `g_slot_sequences` and `g_effect_queue` are process-wide. Stop and unload them at a world switch.
- **Identity and host singletons (chronicle:port/src/identity.cpp:6-12; kazarov:src/cpp/platform/window.cpp:16-20).** The window, renderer, audio stream, clock and input are one per process. A combined build needs one shared identity, and per-world config and save folders below it.
- **Symbol isolation.** Put each game's translation units in a namespace, or link each game as its own object library, and resolve the shared C names (`WorkBuffer`, `GlobalDataBuffer`, `SaveData`) per game (chronicle:port/src/linknames.cpp:32-33).

## Risks and blockers

- **Zeroing across games.** `ArenaClearAll()` zeroes every live block. A second game's startup or scene reset would wipe the first game's live arenas unless the domain change above is made first (kazarov:src/cpp/platform/arena.cpp).
- **Address space and commit.** A single DC1 dungeon reserves about 181 MB and a DC2 dungeon will have its own budget. Windows commits the whole mapping at map time (kazarov:src/cpp/platform/memory.cpp), so two worlds resident together could hit the commit limit before physical RAM runs out. Inference.
- **Retired blocks never unmap.** Each growing carve of an arena retires its old block. Retired blocks are decommitted, so only address space is lost. Repeated growth over a long session accumulates reservations. Inference.
- **Truncated pointers.** The port's arenas sit above 4 GiB, and the one DC1 mechanism for 32-bit pointer fields (`PortImagePointer`) recovers only image pointers. Any DC2 code that stores an arena pointer in an `s32` will break when DC2 runs in the same process. DC2's own truncation log lists two open round trips, but both are in functions marked "not linked" (chronicletwo:docs/port/truncations.md, open round trips). Check again once DC2 is linked.
- **Debug-only guard.** `ArenaRequireOneAbove4GiB` runs only in debug builds (kazarov:src/cpp/platform/arena.cpp:80-88). A release build would not catch a mapping that drifted low.
- **Adjacency assumptions.** The editor's `InitWorkBuffer` (chronicle:ps2/src/editloop.cpp:502-514) assumes the 0x180000 bytes before `read_buffer` belong to the editor, which the lead in chronicle:port/src/dataset.cpp:12 provides. The editor's NPC offset `+ 0xCF8500` (editloop.cpp:762) assumes a fixed layout inside `DataBuffer__2`. Any change to carve order or arena keys breaks these silently.
- **Dangling pointers after reset.** Dungeon state keeps pointers into arenas (`NowDngMap`, `NowColData`, `NowEventMan`, `old_read_buffer`; chronicle:ps2/include/dun/gameloop.hpp:223-262). After `ArenaClearAll`, or after a grow that retires the block, those pointers read zeros. After a plain re-carve they read whatever the previous owner left. Either way they are not freed memory, so a world switch has to clear them explicitly.
- **Static initialisation order.** `TexManager`'s constructor runs `Initialize`, which touches `TextureData`, the texture registry and the render target table, in an order the port does not control (chronicle:port/src/texture_port.cpp:50-53). A second game's manager would add more constructors in the same unspecified order.
- **Shared owner key.** Texture entries owned by `Manager` are released together (chronicle:port/src/texture_port.cpp:410-416). Two managers in one process would release each other's entries.
- **Layout drift.** The port's host-sized structs (`OBJ_ANIME_SEQ`, `CWater`, and others, chronicle:port/src/title/title_layout.cpp:18-21) differ from the PS2 layouts. Any code that assumes PS2 sizes in a second game will misread them.

## Open questions

1. Retail `InitializeDataBuffer` resets `GlobalDataBuffer.used` but not the `VisualData`, `MotionData` and `TextureData` bases set by `BufferAllClear`, so the newly carved `WaterData`, `ActiveData0` and `ActiveData1` land on top of regions those older arenas still point at (chronicle:ps2/src/dataset.cpp:44-64, 97-130). The dungeon load re-carves `MotionData` and `TextureData` but not `VisualData`. Does any dungeon-path code allocate into `VisualData` after the reset? The port's per-key carve avoids the overlap, so a PS2-faithful behaviour would differ. Needs a trace.
2. Is `static CSaveData save_data` (chronicle:ps2/src/main.cpp:118) actually unreferenced in the PC build? A linker map would settle it.
3. Exact PC sizes of the largest statics. The figures here come from address gaps. A PE map file or DWARF would give exact values.
4. Does Windows charge commit for the 27 MB zero-initialised block in the image's `.data` section? If yes, it counts against the commit limit even though the port never touches it.
5. The texture registry's entry size (about 80 bytes estimated, about 1.3 MB for 16,384 entries) and the `CTexture` array size (196 entries) need measurement.
6. Is `CTextureManager::Initialize` called more than once per process on any path? Only if `TexManager` is re-initialised across modes, which would affect the multi-game plan.
7. The PS2 `CDataAlloc2` used a 32-bit `base`. Do any retail call sites depend on arithmetic over `base` that would overflow a 64-bit host pointer if the arena were placed high? The truncation log says no round trips run, but this is worth a targeted test with arenas pinned below 4 GiB.
