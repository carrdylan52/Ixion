# Chronicle main loop and control flow

## What this covers

How the Chronicle (DC1) PC port runs its game: process entry, the mode state machine that `RunGame` drives, the logic clock that stands in for the PS2 VSync interrupt, how a frame ends and is presented, how waits behave, shutdown, and which OS threads exist. It also answers the Ixion question: can a host suspend the game between frames, resume it later with state intact, and where would a "yield to host / swap to the other game" call go.

Citations: `chronicle:` is the Chronicle checkout (master 3bc16763). `kazarov:` is the Kazarov submodule at its current layout (main 9310c53). Chronicle pins Kazarov a0a5ff8, which uses an older layout (`port/platform/`, `port/sce/`). The clock and thread sources are identical between the two apart from include paths (checked with `diff`), so the current paths are used and the pinned path is noted where it matters.

## Key facts

- **Entry point.** `main` is a `PORT_OVERRIDE` in `chronicle:port/src/main.cpp:471-473`. It calls `Run` (`chronicle:port/src/main.cpp:367-467`). On Windows, `wmain` (`chronicle:port/src/main.cpp:650-661`) converts arguments and calls the same `Run`.
- **PS2 startup is not compiled.** `chronicle:ps2/src/crt0.s` (`_start` at line 46, `jal main` at line 96) is assembly and the port's CMake globs only `*.cpp` (`chronicle:port/CMakeLists.txt`, the `PS2_SOURCES` glob). The port's `main` replaces it, and `init_all` (IOP boot, CD and DMA reset) is not called (`chronicle:port/src/gameloop.cpp:792-794`).
- **PS2 `main` never returns.** Its mode loop is `while (1)` (`chronicle:ps2/src/main.cpp:561`). The port's `RunGame` returns `kExitOk` at a frame boundary (`chronicle:port/src/gameloop.cpp:917-918`) so `Run` can shut down.
- **Start-up order in `Run`.** Config and first-run check (`chronicle:port/src/main.cpp:372-410`), then window and input (`:414-419`), renderer (`:421-432`), audio output (`:437`), then the clock: tick rate (`:439`), unbounded flag for headless (`:440`), pump hook `PumpHost` (`:441`), frame budget (`:442`), present settings (`:444`), config change hooks (`:445-448`), and finally `RunGame` (`:450`).
- **`RunGame` has two nested loops.** The outer `for (;;)` (`chronicle:port/src/gameloop.cpp:864`) handles mode changes: `initialize_data` once, `InitReadBG`, `SndInit`, `LoadOverlay`, `ModeInit`, the loading spin, and the map-jump follow-up. The inner `do { ... } while (result == 0)` (`:916-955`) is the frame loop.
- **One inner iteration is one frame.** It runs `MGBeginFrame`, `SetEnv`, one call to `ModeLoop` (`:928`), `GameApplyLoopResult` (`:929`), the language re-load check (`:930-938`), `GiveOnArrival`, pad update and step, `MGEndFrame` (`:946`), `++g_frames` (`:947`), `PresenceTick`, the debug-chord check and the developer-menu check (`:950-954`). The loop ends when a mode's loop returns non-zero.
- **Each mode's loop is one call per frame.** Examples: `GameLoop` (`chronicle:ps2/src/dun/gameloop.cpp:1977`), `EditLoop` (`chronicle:ps2/src/editloop.cpp:1168`), `TitleLoop` (`chronicle:ps2/src/title/titleloop.cpp:440`), `OpeningLoop` (`chronicle:ps2/src/title/opening.cpp:513`), `RushLoop` (`chronicle:ps2/src/title/rushmovi.cpp:404`), `MenuLoop` (`chronicle:ps2/src/main.cpp:1087`). State lives in globals and statics. `ModeLoop` dispatches on `mode` (`chronicle:port/src/gameloop.cpp:303-342`).
- **"One call, one frame" is nearly but not quite an invariant.** `EditLoop` ends and starts ticks inside a single call during its fade paths: `MGEndFrame` and `MGBeginFrame` at `chronicle:port/src/editloop.cpp:250` and `:258`, and `:544` and `:558`, with `sceGsSyncV` spins at `:242-245`. Load code in mode units spins on `wait_now_loading_vsync` (for example `chronicle:ps2/src/dun/gameloop.cpp:1265, 1309, 1327, 1367`; `chronicle:ps2/src/title/title.cpp:330`), and each of those pumps the clock. The ps2 tree has `MGEndFrame` calls only in `editloop.cpp` (lines 1230, 1522), `main.cpp` (960, 974) and `mglib.cpp` (the definition).
- **Frame budget and stop.** Globals `g_frame_budget`, `g_frames`, `g_stop` (`chronicle:port/src/gameloop.cpp:211-213`). `FrameBoundaryStop` (`:392-394`) is tested at the top of the inner loop (`:917`), so a stop lands at a frame boundary and never mid-frame. `GameRequestStop` sets `g_stop` (`:671-673`). Nothing in the tree clears it: `g_stop` is assigned only at line 672.
- **The logic clock is the VSync stand-in.** Kazarov's `platform/clock` counts ticks; one tick is one VSync (`kazarov:include/platform/clock.hpp:6-29`). The count is derived from wall time against an anchor (`kazarov:src/cpp/platform/clock.cpp:46-63`, `Deadline` and `TickAt`). An overrun makes the count jump; the logic does not run extra frames to catch up (`kazarov:include/platform/clock.hpp:8-12`).
- **`ClockPump`** (`kazarov:src/cpp/platform/clock.cpp:133-160`): if already pumping it returns at once (`:134-136`). Otherwise it advances the count to the target tick. It calls the tick callback once per elapsed tick (`:145-151`), then runs every pump hook in order (`:153-155`), then the single idle hook (`:156-158`). A `Guard` sets `pumping` for the duration (`:138-142`).
- **Waits pump the host.** `ClockWaitNextTick()` sleeps to the next deadline, sleeping most of the way and spinning the last 1.5 ms (`kazarov:src/cpp/platform/clock.cpp:65-72`, `:166-172`). `ClockSyncV` is wait-then-pump (`:194-197`). `sceGsSyncV` is `ClockSyncV() & 1` (`kazarov:src/cpp/sce/libgraph.cpp:7-9`). The game's VSync spins (`ReadBGSync`, `check_now_loading`, `CGamePad::Init`) therefore all pump the host.
- **Default tick rate is 60 Hz.** `kazarov:include/platform/settings.hpp:50`, overridable with `game.tick_rate` (`chronicle:port/src/platform/config.cpp:397-405`). Documentation disagrees: `chronicle:docs/DECOUPLING_PLAN.md:146` and `chronicle:docs/PC_PORT_PLAN.md:31` say 50. `chronicle:docs/PC.md:5-7` says the game runs 60 ticks a second and that the PAL speed-up (`#ifdef PAL_TIMING`, used in `chronicle:ps2/src/chararead.cpp:408` and `chronicle:ps2/src/dun/gameloop.cpp:7749` and later) is left out. `chronicle:port/CMakeLists.txt` says the port is always the PAL release.
- **Frame end.** `MGEndFrame` (`chronicle:port/src/mglib.cpp:600-654`):
  1. Picking reads (`:601-615`).
  2. If recording, `EndRecording` and `GameRenderTick` (`:619-624`). `GameRenderTick` renders the canonical image synchronously on the game thread (`chronicle:port/src/gameloop.cpp:694-710`).
  3. If `mgWaitVSync` is zero, pump (`:643-645`).
  4. If no tick has passed yet, `ClockWaitNextTick(GamePresentBetweenTicks)` (`:646-649`), then pump again.
  5. `GamePresentTickEnd` (`:651`), then the double-buffer flip (`:653`).
- **Modes can force waiting.** `MGFlipWaitVSync` (`chronicle:port/src/mglib.cpp:656-658`) sets `mgWaitVSync`, which makes every `MGEndFrame` wait for the next tick. It is used by the edit code (`chronicle:ps2/src/edit.cpp:2059, 2128`; `chronicle:ps2/src/editloop.cpp:713, 1653`; `chronicle:port/src/editloop.cpp:675`).
- **Display frames between ticks.** `GamePresentBetweenTicks` (`chronicle:port/src/gameloop.cpp:712-743`) presents interpolated display frames while the game waits for a tick, paced by `max_fps` if set. With interpolation off (`chronicle:port/src/gameloop.cpp:717-723`), it presents the canonical image once per tick. Interpolation defaults on (`chronicle:port/src/platform/config.hpp:41`). `GamePresentTickEnd` (`:745-758`) presents the canonical image if nothing was shown during the tick.
- **Window events and input sample only on pumps.** `PumpHost` (`chronicle:port/src/main.cpp:221-238`) polls window events (`WindowPollEvents`, a false return calls `GameRequestStop`), display, layout, input, and the input script. The pump hooks run on every `ClockPump` call, not once per tick: `ClockPump` runs them even when the count did not advance (`kazarov:src/cpp/platform/clock.cpp:153-158`). `MGEndFrame` pumps before and after its wait (`chronicle:port/src/mglib.cpp:643-649`), and waits inside modes pump too. The between-tick display path (`GamePresentBetweenTicks`) does not pump.
- **Input scripts count frames, not ticks.** `InputScriptApply(GameFrameCount())` (`chronicle:port/src/main.cpp:237`). Fade ticks inside `EditLoop` add ticks without adding frames.
- **Headless is deterministic.** `ClockSetUnbounded(options.headless)` (`chronicle:port/src/main.cpp:440`). Each pump advances exactly one tick and waits return at once (`kazarov:src/cpp/platform/clock.cpp:166-169`, `:183-186`). The C `rand` is replaced by a fixed generator (`chronicle:port/src/runtime.cpp:24-42`) so runs repeat.
- **Shutdown.** `RunGame` returns, then `Run` takes the screenshot if asked (`chronicle:port/src/main.cpp:451-453`), reports stats (`:454`), removes its hooks (`:456-460`), and stops Discord, audio, input, the renderer and the window (`:461-465`). No save is written on this path. `ConfigSave` runs on a config change and when no config file exists yet (`chronicle:port/src/platform/config.cpp:684-691`, `:693-711`, `:727-748`).
- **Assertions bypass shutdown.** `__assert` prints and calls `std::_Exit` (`chronicle:port/src/runtime.cpp:13-18`), so static destructors and the renderer teardown do not run.
- **Transitions are a table, not a call stack.** `GameFollowMapJump` (`chronicle:port/src/gameloop.cpp:409-445`) maps `NextMapNo` to a mode: under 200 is `GAME_MODE_EDIT` (towns and interiors), 200 to 299 is `GAME_MODE_DUNGEON`, 400 is `GAME_MODE_OPENING`, 800 and up is title or rush. `GameApplyLoopResult` (`:447-551`) maps each mode's loop result to the next mode. Mode values are in `chronicle:ps2/include/main.hpp:14-29`.
- **Each transition ends with a blank tick and a drain.** `RunGame` runs one extra `MGBeginFrame`/`MGEndFrame` pair (`chronicle:port/src/gameloop.cpp:957-958`), then `GameFollowMapJump` and the trial-end check (`:960-965`), then drains `ReadBGSync` (`:969-971`).
- **Threads.** The game's own code creates no threads. `CreateThread`, `StartThread`, `WaitSema` and `SignalSema` appear nowhere in `chronicle:ps2/src` or `chronicle:port/src`. Kazarov does implement PS2 threads as fibers or `ucontext` on the main OS thread (`kazarov:src/cpp/sce/eekernel_threads.cpp:19-20`, scheduler at `:203-217`, `CreateThread` at `:248`, `WaitSema` at `:354`, `SignalSema` at `:380`), and it aborts a switch inside `ClockPump` (`:207-212`). For Chronicle the scheduler is dormant.
- **Other OS threads.** The SDL audio callback `Feed` (`kazarov:src/cpp/platform/audio.cpp:71-86`, opened at `:150`) calls the mixer's `Render`, which takes a mutex (`kazarov:src/cpp/audio/mixer.cpp:655`). The Discord worker is a `std::thread` (`chronicle:port/src/platform/discord.cpp:393`), joined in `DiscordStop` (`:404-414`). The first-run extraction worker is a `std::thread` (`chronicle:port/src/platform/firstrun.cpp:389`) and runs before `RunGame`, with its own event loop.
- **Renderer work is on the game thread.** Tick renders go through `gfx::RenderList` from `GameRenderTick` (`chronicle:port/src/gameloop.cpp:694-710`). The frame-level `gfx::EndFrame` (`kazarov:src/cpp/gfx/renderer.cpp:1098`) is reached from `MGEndFrame` only outside a recording (`chronicle:port/src/mglib.cpp:626`), and from the loading screen (`chronicle:port/src/nowload.cpp:143-158`). `gfx::BeginFrame` is at `kazarov:src/cpp/gfx/renderer.cpp:1080`. Swapchain acquire blocks with an infinite timeout (`:927`), and presentation is `vkQueuePresentKHR` (`:982`).
- **Loading screen.** `check_now_loading` is `ClockSyncV` while `end_flag` is zero (`chronicle:port/src/nowload.cpp:161-166`). The loading screen presents from the idle hook (`chronicle:port/src/nowload.cpp:143-158`, set at `:252`), outside any open frame. A comment there notes that a mode's Init can be between `MGBeginFrame` and `MGEndFrame` when it waits.

## How it works

**Boot.** `Run` parses options, resolves the data and save directories, optionally jumps to a test mode (`--jump`), checks for game data, creates or loads `config.json`, opens the window and renderer, starts audio, and installs the pump hook. It then calls `RunGame`. `RunGame` (`chronicle:port/src/gameloop.cpp:791`) sets `DebugMode` from config, sets `mode` to the menu, calls `InitCDFile`, initialises the memory file and background reader, zeroes the save data, runs a 60-tick warm-up (`kWarmUpTicks`, `:71`, skipped on a jump), and then chooses the first mode: the language screen, or straight to the rush movie when the data holds only one language or config names one (`:838-850`). A jump instead calls `ApplyJump` (`:353-390`).

**Mode machine.** The outer loop runs per mode change. For each mode it calls the mode's `Init` (`ModeInit`, `:223-287`), spins on `check_now_loading` until the loading screen ends (`:906-907`), sets the VSync callback to `PlayTimeCount` (`:909`), and syncs the clock (`:911`). Then the inner loop runs frames until the mode returns non-zero. The result goes through `GameApplyLoopResult`, and the next mode comes from `mode`, `NextMapNo` (through `GameFollowMapJump`), or the trial-end check. Retail's `main` in `chronicle:ps2/src/main.cpp:436-974` has the same shape. The port drops the memory-card check that retail ran after the language screen (`chronicle:port/src/gameloop.cpp:450-455`), and adds the developer menu (`GameDeveloperMenuRequested`, `:623-630`).

The mode table, as the port dispatches it (`ModeInit` `chronicle:port/src/gameloop.cpp:223-287`, `ModeLoop` `:303-342`, transitions `GameApplyLoopResult` `:447-551`; enum values in `chronicle:ps2/include/main.hpp:14-29`):

- `GAME_MODE_TITLE` (0): `TitleInit`/`TitleLoop`. Result 1 starts a new game: the mode is set to the editor, then `MapJump(400)` and `StartNewGame` run, and `GameFollowMapJump` turns the pending 400 into the opening. Result 2 sets the editor on its second entry; 3 goes to a dungeon; 4 jumps to the rush movie; 5 goes to the opening.
- `GAME_MODE_RUSH_MOVIE` (1): `RushInit`/`RushLoop`. Any non-zero result jumps to title (800).
- `GAME_MODE_EDIT` (2): `EditInit`/`EditLoop` (towns and the Georama editor). The checks run in order, so results 1 and 2 are overwritten by the "any non-zero goes to the menu" check and end in the developer menu; only 3 goes to a dungeon (`chronicle:port/src/gameloop.cpp:486-496`, with the comment "as retail tests them").
- `GAME_MODE_DUNGEON` (3): `GameInit`/`GameLoop` (the default branch in both switches). Non-zero result to the menu.
- `GAME_MODE_OPENING` (5): `OpeningInit`/`OpeningLoop`. Non-zero result to title, then a jump to 0.
- `GAME_MODE_MENU` (7): `MenuInit`/`MenuLoop`. Circle returns -1 (`ModeLoop`, `:318-319`), which returns to the developer-return mode or title.
- `GAME_MODE_LOADER` (9): `LoaderInit`/`LoaderLoop`. Result 2 to menu, otherwise to dungeon.
- `GAME_MODE_MEMORY_CHECK` (10), `GAME_MODE_TRIAL_END` (11), `GAME_MODE_SAVE` (13), `GAME_MODE_LANGUAGE` (14): their own Init and Loop, then the menu, rush or title as in `GameApplyLoopResult`.
- `GAME_MODE_UNUSED_6`, `_8`, `_12`: no-op loops (`ModeLoop` returns 0, so these run idle frames).

Each mode change also goes through `GameFollowMapJump` (`chronicle:port/src/gameloop.cpp:409-445`), which turns `NextMapNo` into `mode` and `MapNo`, so a jump to a map number can change the mode as well.

**Frame timeline.** One inner iteration of `RunGame`, in order:

1. `FrameBoundaryStop` check (may return from `RunGame`).
2. `MGAdjustScreen`, `ConfigWords` game-clear write, then `MGBeginFrame` (opens a recording if none is open).
3. `SetEnv` (state words only, `chronicle:port/src/gameloop.cpp:682-687`), `PolyCount` reset, `old_main_mode`.
4. `ModeLoop`: one call to the current mode's Loop. This is where the frame's game logic runs; nested waits and fades inside it can add ticks, and the tick callbacks those pumps run also execute game code (see Key facts).
5. `GameApplyLoopResult`, then the language re-load check.
6. `GiveOnArrival`, `InputSetLookOnLeftStick`, `GamePad.UpDate`, vibration, `GamePad.Step`.
7. `MGEndFrame`: render the recording, pump, wait if needed, present, flip.
8. `++g_frames`, `PresenceTick`, `GameCheckDebugToggle`, `GameDeveloperMenuRequested` (may break out to the menu).

**A frame.** Between `MGBeginFrame` and `MGEndFrame`, the mode's loop builds a display list (`gfx::BeginRecording` at `chronicle:port/src/mglib.cpp:556`). `MGEndFrame` ends the recording, renders it as the canonical image, and then decides how long to wait. If a tick has already passed while the frame was built and `mgWaitVSync` is zero, the frame continues straight into the next one with no wait. Otherwise the thread waits. Each wait is turned into a series of display-frame presents when interpolation is on. The count then advances as the clock pumps, which runs window events, input, the tick callbacks and the idle hook.

**Tick clock.** The clock is anchored to wall time. `Deadline(n)` is the wall time of tick `n`. Each pump computes the target tick from the current time and runs the callback once per tick it passes. A slow frame gets no extra logic frames: the callback (for example `PlayTimeCount`) runs for each missed tick, but the game's frame runs once, so the game slows down rather than catching up. This matches the comment in `kazarov:include/platform/clock.hpp:8-12`.

**Presentation.** A tick is shown either as interpolated display frames interpolated from the last two lists (`gfx::RenderList` with an alpha, `chronicle:port/src/gameloop.cpp:170-184`), or as the canonical image once. Display frames are paced by `max_fps` if set; otherwise the present mode (`Fifo`, `Mailbox` or `Immediate`, `chronicle:port/src/platform/config.cpp:62-80`) is the only limit, which is inference from the code path rather than a traced pace. The FPS overlay is drawn only into the presented image (`chronicle:port/src/gameloop.cpp:150-195`).

**Waiting inside a mode.** Many load and fade paths sit inside a mode's Init or Loop and spin on the clock. Each spin pumps the host, so window events and input keep flowing, and the idle hook presents the loading screen during loads. A spin inside an Init does not return to `RunGame` until it is done. Only `EditLoop`'s fade paths also end and start frames inside a call.

**Shutdown.** Window close (`WindowPollEvents` returns false) calls `GameRequestStop`. The game finishes the frame it is in, then `RunGame` returns at the top of the next inner iteration. An in-progress nested spin does not check `g_stop`, so a close during a long load waits for the load to finish (inference from the loops at `chronicle:port/src/gameloop.cpp:906-907` and `chronicle:port/src/nowload.cpp:161-166`). `Run` then tears down in reverse order.

## Ixion hooks

- **`RunGame` inner-loop top, `chronicle:port/src/gameloop.cpp:916-919`.** This is the only existing clean point: outside any frame (`gfx::Recording()` is false by then), with all mode state in globals. The `FrameBoundaryStop` test is already here, and a true result returns from `RunGame` without tearing anything down. Ixion could split `RunGame` into an init part and a `GameStepFrame()` that runs one inner iteration (lines 917-955) and returns, so a host drives the loop. The blocker is the nested spins described under Risks.
- **`GameRequestStop` and `GameStopRequested`, `chronicle:port/src/gameloop.cpp:671-677`.** The one-way stop is a model for a host pause flag. It needs a reset (see Risks), and a paused return would have to leave game state alone; today every return from `RunGame` leads into `Run`'s teardown.
- **Between-tick wait, `chronicle:port/src/mglib.cpp:646-649` with `GamePresentBetweenTicks`.** This is the only in-frame wait that hands the host a callback with a deadline (`ClockWaitHook`, `kazarov:include/platform/clock.hpp:33-36`; `ClockWaitNextTick(hook)` is called from this one site in the port, `chronicle:port/src/mglib.cpp:647`). A host could run short slices of other work here. Two things block using it to run another game's frame: the slice has to end before the next tick, and the other game's globals and clock would have to be separate.
- **Pump hook, `chronicle:port/src/main.cpp:221-238`, registered at `:441`.** Runs on every pump with input and window events, so it is a plausible place to route input between worlds or handle a host-level request (inference). It must not switch stacks: `ClockPumping` is set (`kazarov:src/cpp/platform/clock.cpp:138-142`), and the scheduler aborts a switch there (`kazarov:src/cpp/sce/eekernel_threads.cpp:207-212`).
- **`GameFollowMapJump` and `GameApplyLoopResult`, `chronicle:port/src/gameloop.cpp:409-551`.** A cross-world visit could enter as a new range of `NextMapNo` or a new result code handled here. The mode dispatch in `ModeInit` (`:223`) and `ModeLoop` (`:303`) is where the mode changes take effect.
- **Frame budget, `GameSetFrameBudget` and `--frames`, `chronicle:port/src/gameloop.cpp:663-669` and `chronicle:port/src/main.cpp:442`.** A bounded run stops cleanly at a frame boundary, which makes it a usable test hook for any swap experiment.
- **Unbounded clock, `kazarov:src/cpp/platform/clock.cpp:166-186`.** In headless mode each pump is exactly one tick. Two games stepped by one host on one clock would advance in lockstep, if they could share the clock (inference).
- **Config change hooks, `chronicle:port/src/main.cpp:445-448`.** Settings changes reach the game through these. They are not a switching mechanism but show the pattern for host-to-game notification.

## Risks and blockers

- **No resumable entry.** `RunGame` is terminal. `g_stop` is never cleared (`chronicle:port/src/gameloop.cpp:672`), so a second `RunGame` in the same process repeats the start-up work (including the save-data `memset`) and then returns at the first frame boundary (`chronicle:port/src/gameloop.cpp:917`). Even with `g_stop` cleared, `RunGame` re-initialises everything: `DebugMode`, the mode, `InitCDFile`, `MGInit`, and a `memset` of the save data (`chronicle:port/src/gameloop.cpp:795-829`). Calling it again to "resume" would wipe the save. A swap cannot be done by re-entering `RunGame`.
- **Mid-mode suspension needs stack switching.** Nested spins (`wait_now_loading_vsync`, `ReadBGSync`, `check_now_loading`, the `EditLoop` fades) keep the call stack deep inside one frame. Suspending there requires a separate stack. Kazarov has the mechanism (fibers, `kazarov:src/cpp/sce/eekernel_threads.cpp:19-20`, with `ucontext` included at `:32`) but Chronicle never uses it, and switching is forbidden inside `ClockPump`. A suspend at a frame boundary avoids this only when the mode's Loop has returned and no nested spin is open.
- **Global state.** Game state is file-scope or C-linkage globals: `mode`, `MapNo`, `NextMapNo`, `SaveData`, `GamePad`, `DebugMode`, `PolyCount`, and the mode units' statics (for example `static int end_count` in `chronicle:ps2/src/editloop.cpp:1179`, and the static menu table inside `MenuLoop`, `chronicle:ps2/src/main.cpp:1087`). Two games in one image need renaming or separate images. Both trees define `main`: Chronicle's is `chronicle:port/src/main.cpp:471` (a `PORT_OVERRIDE`) and its PS2 original is `chronicle:ps2/src/main.cpp:436`; ChronicleTwo has `chronicletwo:port/src/main.cpp:332` and `chronicletwo:ps2/src/main.cpp:138`. This points to separate processes or separately namespaced shared objects; the c2 researcher should confirm the rest of the symbol overlap.
- **Kazarov singletons.** The clock state (`clock.cpp:18-32`, with the pump hook list and the single tick callback and idle slot, `:107-125`), the scheduler (`eekernel_threads.cpp`, static in `Sched()`), the renderer's global context, the SDL window and the audio mixer are all process-wide. A second game in the same process shares them, or, if each game links its own copy, gets its own clock and window (inference). Shared is the only way the two could agree on tick and present timing.
- **One tick callback slot.** `ClockSetTickCallback` (`kazarov:src/cpp/platform/clock.cpp:107-109`) holds one callback, and `MGInitVSyncCallBack` sets it per mode (`chronicle:port/src/mglib.cpp:544-546`). A second game's callback would replace the first's.
- **Tick rate conflict.** Code defaults to 60 Hz (`kazarov:include/platform/settings.hpp:50`). `docs/PC.md:5-7` says the PAL 50 Hz speed-up is left out. If one game's logic was tuned to PAL timing, running both on a single 60 Hz clock would speed that game up by about 20 percent if its logic runs once per tick (inference from the 60/50 ratio). Confirm the c2 tick assumptions before choosing one clock.
- **Frame-keyed input.** `InputScriptApply` and the frame budget count frames, not ticks (`chronicle:port/src/main.cpp:237`, `chronicle:port/src/gameloop.cpp:947`). Fade ticks inside `EditLoop` advance the clock without advancing these. A swap that changes frame counts changes script timing.
- **Unsaved progress on close.** The shutdown path writes no save (`chronicle:port/src/main.cpp:450-466`). A host that swaps or closes must save first, through the game's own save screen (`GAME_MODE_SAVE`, `chronicle:port/src/gameloop.cpp:322-323` for the loop); `chronicle:port/src/platform/config.cpp` writes `config.json` only.
- **Crashes are not contained.** `__assert` exits the whole process with `_Exit` (`chronicle:port/src/runtime.cpp:13-18`). A fault in one game ends both.
- **Audio thread.** The mixer renders on SDL's thread under a mutex (`kazarov:src/cpp/audio/mixer.cpp:655`). A host that swaps mixer sources must take the same lock, and the swap must not race the `Feed` callback.
- **Nested ticks.** `MGEndFrame` can run more than once per `RunGame` frame (from `EditLoop`). A hook placed at `MGEndFrame` or in the pump fires more often than the frame counter suggests.
