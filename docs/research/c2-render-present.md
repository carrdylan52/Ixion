# ChronicleTwo: rendering and presentation

## What this covers

How the ChronicleTwo (DC2, Dark Chronicle) PC port turns the game's PS2 graphics calls into Vulkan frames and window presents, and what that implies for Ixion running two games in one window on one device. Covered: the `port/src` replacements for the `mg*` graphics units (`mglib`, `mg_drawprim`, `mg_texture`, `mg_visual`, `mg_sprite`, `mg_shadow`, `mg_frame`, `mg_tanime`), the VU1 CPU stand-ins (`port/src/vu1/`), the presentation driver (`present.cpp`, `present_timing.hpp`), the screen-overlay anchor, outline and screen effects, and the Kazarov graphics and window layer that the port links (`gfx/`, `platform/window`, `platform/display`, `platform/clock`, `platform/overlay`).

Pinned Kazarov in this checkout is `3dc38ce`, the current layout. Its `gfx/` and `platform/` trees are identical to Kazarov `main` (`9310c53`) (no diff between the two commits in those paths), so the reading below holds for either. The older Kazarov pin used by Chronicle DC1 (`a0a5ff8`) has the same API surface apart from `SetInterp2D`, but puts the headers under `port/gfx` and `port/platform`.

Not covered in depth: the sound path, the game's thread emulation (`sce/threads`), the first-run setup window, and the content of the `ps2/src` units beyond their graphics calls.

## Key facts

- **One process, one window, one renderer, one device.** Each game's `main()` opens the window and creates the renderer, then calls `MainLoop()`: `chronicletwo:port/src/main.cpp:279` (`WindowInit`), `:295` (`RendererInit`), `:317` (`MainLoop`), `:325-326` (shutdown). The window is a file-static `g_window` in `kazarov:src/cpp/platform/window.cpp:16`; the renderer's whole state is a single static `Context g` in `kazarov:src/cpp/gfx/renderer.cpp:20`. `RendererInit` resets it with `g = {}` (`renderer.cpp:796`), so a second init without a shutdown has no defined meaning.
- **Window ownership.** `WindowInit` calls `SDL_Init(SDL_INIT_VIDEO)` and `SDL_SetAppMetadata` (`window.cpp:58-73`); `WindowShutdown` calls `SDL_Quit` (`window.cpp:161-167`). Window events go through a process-global hook list `g_hooks` (`window.cpp:19`, `:224-249`). A close request returns false from `WindowPollEvents`, and the game's `PumpHost` answers it with `std::exit(kExitOk)` (`chronicletwo:port/src/main.cpp:215-218`).
- **Vulkan ownership.** The renderer creates the instance, the surface (`SDL_Vulkan_CreateSurface`, `renderer.cpp:805`), the device, the swapchain and two frames in flight (`kFramesInFlight = 2`, `kazarov:include/gfx/context.hpp`). The device is picked for present support against that surface (`renderer.cpp:158-170`).
- **The swapchain is only a blit destination.** `PresentImage` blits any renderer colour image (the canonical main colour, or the window-sized display image) into the acquired swapchain image with `vkCmdBlitImage` (`renderer.cpp:950-975`). Game content is never rendered straight into a swapchain image. Resizes arrive as `SDL_EVENT_WINDOW_PIXEL_SIZE_CHANGED`, which calls `RendererResize` (`window.cpp:236-238`) and recreates the swapchain lazily (`renderer.cpp:921-940`).
- **Fixed at init.** `RendererConfig` carries the logical size (`logical_width`, `logical_height`), `display_aspect`, `prog0_meshes`, `offscreen`, the pipeline cache path and the initial layout (`kazarov:include/gfx/gfx.hpp`, struct `RendererConfig`). The logical size has no setter after init (`logical_width` is read once, `renderer.cpp:794-828`). Runtime setters exist for present mode (`SetPresentMode`, `renderer.cpp:892-897`), frame layout (`SetFrameLayout`, which recreates render targets, `renderer.cpp:1149-1162`), render scale, anisotropy and UI anchor (unverified).
- **ChronicleTwo's renderer config.** Logical 512x480, display aspect 4:3, `prog0_meshes = true` (which precompiles the Vu_prog0 mesh families), pipeline cache under the save root (`chronicletwo:port/src/main.cpp:43`, `:285-295`; `docs/PC.md`, "Startup", step 6). Layout is `video.aspect` (auto means `AspectMode::Fill`, 4:3 means `Letterbox`) and `video.ui_scale` (`main.cpp:200`; `docs/PC.md`, "config.json").
- **Recording model.** `mgBeginFrame` opens a display-list recording with `gfx::BeginRecording()` (`chronicletwo:port/src/mglib.cpp:1195-1240`). Draws between `mgBeginFrame` and `mgEndFrame` are recorded, not presented. `mgEndFrame` seals the list and renders it canonically with `RenderList(..., {.canonical = true})` (`mglib.cpp:1296-1300`), keeps the previous and last lists (`:1303-1304`), calls `PresentTickRendered` (`:1305`), then `PresentWaitFrame` (`:1354`) and `PresentTickEnd` (`:1356`).
- **The game frame is paced by the wait, not by the draw.** `mgFrameRate = 2` ticks per game frame (`mglib.cpp:1113`, `mainloop.cpp:236`). `PresentWaitFrame` runs `BetweenTicks` through `mgTimeWaitTicks`, which renders display frames from the newest and previous lists at alpha values across the game frame (`present.cpp:154-190`, `:240-244`). If none was shown, `PresentTickEnd` presents the canonical image (`present.cpp:246-261`).
- **Presentation is a process singleton.** `present.cpp` keeps its settings, pacer, FPS overlay and counters in anonymous-namespace globals (`present.cpp:35-40`). Its list sources are the globals `mgPortLastList()` and `mgPortPreviousList()` (`mglib.cpp:77-78`, `:1023-1030`).
- **The presenter also pumps input and events.** The overlay path calls `WindowPollEvents()` and `InputPoll()` while a mouse pointer or fixed look is active (`present.cpp:51-57`).
- **Draw submission.** `mgPortDraw2D` drops draws unless `ready && gfx_open` (`mglib.cpp:901-905`), scales vertices and scissors by texel scale for scaled targets, then calls `gfx::Draw2D` (`:906-938`). 3D meshes go through `mgPortDrawMesh`, `mgPortDrawMeshImmediate` and the two Prog0 variants (`:940-980`). No PS2 packets are built, and `mgSendVuProg` only records the program id (`mglib.cpp:1633-1636`; `docs/PC.md`, "Packets").
- **3D sprites are 2D draws with depth.** `mgC3DSprite::Draw` expands billboards on the CPU using the `vu1` helpers and submits them as 2D vertices with a `z` value (`chronicletwo:port/src/mg_sprite.cpp:305-330` for `Draw`; `:115-130` for `SubmitSpriteBatch`, which calls `vu1::Sprite3dExpandNative`; `port/src/vu1/sprite3d_geom.cpp`). The renderer tests 2D depth against meshes when projections agree (`kazarov:src/cpp/gfx/README.md`, "Spaces" and "Depth").
- **Textures.** `UploadPixels` creates an RGBA8 `gfx` texture and fills it with `UpdateTexture` (`chronicletwo:port/src/mg_texture.cpp:178-206`). The registry resolves a game texture or TEX0 to a handle through lookups installed by `mgPortSetTextureLookup` (`mglib_port.hpp`; `mglib.cpp:751-822`). The texture table has 8192 slots (`kMaxTextures`, `context.hpp`).
- **Named render targets are global.** `NamedRenderTarget` finds or creates a target by name, and destroys and recreates it if the size, alpha, depth-sharing or frame shape differs (`kazarov:src/cpp/gfx/resources.cpp:602-622`). ChronicleTwo uses names such as `"mglib frame grab"` (`mglib.cpp:839`), `"dof frame"`, `"dof level N"`, `"lens flare a"`, `"lens flare b"`, `"lens flare mask"` (`screeneffect.cpp:139-290`), `"outline"` (`outline.cpp:196`) and `"water refraction"` (`water.cpp:185`).
- **kPreviousFrame is coupled to canonical renders.** `kPreviousFrame` is the last canonical render of a display list, or the last frame `EndFrame` finished (`gfx.hpp:154`). ChronicleTwo samples it for the menu grab and blur (`menudraw.cpp:128-137`), `effectlist.cpp:21`, and the PS2-style frame texture mapping (`mglib.cpp:764`).
- **Shadow volumes use the main target's stencil.** `mgBeginDrawShadow` clears stencil when a frame is open (`mglib.cpp:1787-1798`). `mgEndDrawShadow` composites with a stencil-not-equal test that zeroes the count (`mglib.cpp:1800-1820`). Stencil persists across frames until cleared (`kazarov:src/cpp/gfx/README.md`, "Stencil and colour writes").
- **Interpolation state is per-object plus a cut.** Mesh draws are tagged with `mgPortInterpScope(object, ...)` keyed by the object pointer passed in (`mglib_port.hpp:184`; callers such as `mg_visual.cpp:309` and `water.cpp:258`). `mainloop.cpp:258` calls `mgPortCutInterpolation()` at every loop change, and `mglib.cpp:999-1012` forwards the cut to `gfx::CutInterpolation` and camera cuts. `kMgPortFrameTeleportDistance` is 200 units.
- **Clock slots are single.** `ClockSetTickCallback` replaces one tick callback (`kazarov:src/cpp/platform/clock.cpp:107`), and `mgInit` also sets it (`mglib.cpp:1147`), as does `main.cpp:307`. The idle hook is one slot; pump hooks are a list (`kazarov:include/platform/clock.hpp`, `clock.cpp:123`).
- **The main loop does not return.** `MainLoop()` is a `while (1)` over loop modes (`chronicletwo:port/src/mainloop.cpp:73`, `:204`) and only leaves when `PortLoopNo` is out of range. The loading screen draws through the same `mgBeginFrame` / `mgEndFrame` pair (`ps2/src/nowload.cpp:227`, `:274`, `:520`, `:608`, `:703-729`), so it uses the tick path.
- **Mode changes go through one place.** `mainloop.cpp:250-260` says it is the "single entry for every mode change" and cuts interpolation there.
- **Settings are per game.** `GameSetIdentity` sets the env prefix `DC2`, the app directory `chronicletwo`, and the window title and app id (`chronicletwo:port/src/identity.cpp:7-10`). `SettingsSetEnvPrefix` and `PathsConfigure` store process-global state (`kazarov:src/cpp/platform/settings.cpp:5-12`; `paths.hpp`).
- **Chronicle DC1 differs.** Its logical frame is 640x480 (`chronicle:port/src/screen.hpp:4-5`), its env prefix is `DC`, its app directory is `chronicle` (`chronicle:port/src/identity.cpp:9-10`), and its presenter lives in `gameloop.cpp` (`chronicle:port/src/gameloop.cpp:172-189`, `:696`). It builds the same renderer API against the older Kazarov pin.
- **Build override mechanism.** Each `ps2/src` unit is compiled with its `PORT_OVERRIDE` definitions stripped out, and the port's definitions are linked in their place (`chronicletwo:port/CMakeLists.txt:1-10`, `:90-101`; `kazarov:scripts/build/port_override.py` header). The replacements keep the PS2 global names, so `mgInit`, `MainLoop` and `main` are per-binary symbols.
- **Headless and offscreen.** `config.offscreen` skips the surface and swapchain and presents nothing; `EndFrame` submits and returns (`renderer.cpp:813-824`, `:1098-1115`). Headless runs use an unbounded clock (`chronicletwo:port/src/main.cpp:305`; `kazarov:src/cpp/platform/clock.cpp`).
- **Tests exist for this layer.** `chronicletwo:port/src/tests/present_timing_test.cpp`, `mglib_present_test.cpp`, `mglib_aspect_test.cpp`, `mg_drawprim_render_test.cpp`, `mg_shadow_test.cpp` and `vu1_*_test.cpp` cover presentation timing, aspect, drawing and the VU1 stand-ins.

## How it works

**Start-up.** `main` parses options, loads config, and calls `WindowInit` then `gfx::RendererInit` with the game's renderer config (`main.cpp:279-295`). The renderer picks the best device with every required feature, creates the frames and pipelines (about 504 or 840 pipelines depending on `prog0_meshes`, `kazarov:src/cpp/gfx/README.md`, "Pipelines"), and builds main targets at the window's pixel size. `gfx::RendererInit` starts a fresh `Context`, so a second game in the same process would replace the first one's renderer state.

**Each game frame.** The loop calls `mgBeginFrame`, runs the game's logic and draws (recorded into a `DisplayList`), then `mgEndFrame`:

1. Queue depth picks and, if a frame is open, seal the recording (`mglib.cpp:1273-1297`).
2. Render the list canonically into the current main colour image (`RenderList` with `canonical`). This is the image the game's own feedback and screenshots read. Depth queries are answered (`AnswerDepthQueries`).
3. Rotate `last_list` into `previous_list`, record the tick (`PresentTickRendered`).
4. Wait for the rest of the game frame (`PresentWaitFrame`, `mgFrameRate` ticks). During the wait, `BetweenTicks` renders display frames: each is `RenderList(list, alpha, {previous, present=true, overlay})`, which runs the drawing entries into the window-sized display image and presents it (`present.cpp:99-122`, `:154-190`). Interpolation alpha is the fraction of the game frame elapsed (`PresentFrameAlpha`, `present_timing.hpp`).
5. If no display frame was shown, present the canonical image (`PresentTickEnd` to `PresentCanonicalFrame`, `present.cpp:124-152`, `:246-261`).

**Presentation timing.** `PresentPacer` gates display starts at `video.max_fps`. A due logic tick always wins (`present_timing.hpp`, `Next`). `PresentMode` (FIFO, mailbox, immediate) is handed to the renderer (`SetPresentMode`). With `interpolation = false`, each tick is presented once as canonical.

**Window events and input.** `PumpHost` is registered as a clock pump hook (`main.cpp:306`) and polls events, `DisplayPump`, `InputPoll` and the input script, then applies layout changes when none is recording (`main.cpp:215-233`). The presenter also polls while a pointer or fixed look is active (`present.cpp:51-57`).

**Coordinate mapping.** The game works in logical 512x480 space (`chronicletwo:port/src/mglib.cpp:144-166`, `ScreenSizeForMode`). The renderer maps that logical frame onto the window: the largest 4:3 rectangle that fits, centred, scaled per axis (`gfx README`, "Spaces"). Under `Fill`, the window past the frame shows more world at the sides, and `mgPortVisibleExtent` reports what is visible (`mglib_port.hpp`, `mglib.cpp:631-650`). Under `Letterbox`, nothing draws past the frame. Because the logical frame has a 4:3 display aspect, 512x480 logical is stretched by about 1.25 horizontally and 1.0 vertically (inference from the README rule for logical-to-window mapping).

## Ixion hooks

- **Host-owned window and renderer.** Move `WindowInit`, `gfx::RendererInit`, `RendererShutdown` and `WindowShutdown` out of each game's `main` (`chronicletwo:port/src/main.cpp:279-326`) into one host. Games would then receive the window and renderer rather than creating them. This is the precondition for any single-window design, and it only works if the two games can share a process (see Risks).
- **Choose the presenter's list source.** `present.cpp` reads `mgPortLastList()` and `mgPortPreviousList()` (`mglib.cpp:1023-1030`). A host could supply the list and previous list for whichever game is visible, leaving the pacing and interpolation code unchanged. The change point is `DisplayFrame` (`present.cpp:99-122`) and `PresentCanonicalFrame` (`:124-152`).
- **Cut on a world switch.** A visible-game switch is a loop-level change. The existing single entry for mode changes (`mainloop.cpp:250-260`) already cuts interpolation through `mgPortCutInterpolation()`. A switch should call the same cut, and `gfx::CutCameraInterpolation()` if the camera changes (`mglib.cpp:1010-1018`).
- **Present through the display path.** `gfx::RenderList(list, alpha, {.present = true})` presents any recorded list into the window-sized image and does not need the game's canonical image as the output (`kazarov:include/gfx/gfx.hpp`, `RenderOptions`). It is refused when the newest main image is not canonical, so the host must make sure the visible game's canonical render was the last one (`gfx.hpp`, `RenderList` comment).
- **Overlay for transitions and HUD.** `RenderOptions::overlay` draws a second list over the display frame, after the first, uninterpolated, and before present (`gfx.hpp`). A host could draw a world-switch wipe, an Ixion badge, or the FPS counter there. The FPS counter already uses this path (`present.cpp:47-75`; `kazarov:include/platform/overlay.hpp`).
- **Snapshot before crossing.** `gfx::SnapshotFrame` and `CopyTexture` from `kMainTarget` copy the image so that a later draw can sample it (`gfx README`, "Ordering"). A crossfade between the outgoing and incoming worlds could snapshot one, then blend it in an overlay. This is an inference to verify; it has not been tried.
- **Namespace named targets.** Give each game's `NamedRenderTarget` names a prefix (`screeneffect.cpp:139-290`, `outline.cpp:196`, `water.cpp:185`, `mglib.cpp:839`), so one game cannot resize or destroy the other's targets.
- **One logical size.** Pick one logical frame for the renderer. DC1 uses 640x480 (`chronicle:port/src/screen.hpp:4-5`) and DC2 uses 512x480 (`main.cpp:43`). A shared renderer must be initialised with one of them or with a fresh design, since the logical size cannot be changed afterwards.
- **Pipeline cache and feature union.** A shared renderer needs one `RendererConfig`: `prog0_meshes = true` (DC2) with a pipeline cache path that both games can use (`main.cpp:289`, `:293`). DC1 does not set `prog0_meshes`, which is harmless for it.
- **Headless verification.** `RendererConfig::offscreen` and `--offscreen` allow a test harness to render both games' frames to images without a window (`renderer.cpp:813-824`; `docs/PC.md`, "Font and headless"). This is useful for checking a switch.

## Risks and blockers

- **Singleton state everywhere.** The window (`window.cpp:16`), the renderer (`renderer.cpp:20`), the presenter (`present.cpp:35-40`), the mglib state (`mglib.cpp:70-79`), the mouse-look state (`camera_fixed.cpp:225-260` uses function-local statics), the clock (`clock.cpp:30-32`), the settings prefix (`settings.cpp:5-12`) and the path configuration are all process-wide. Two games in one process would share all of them.
- **Symbol collisions in one binary.** Both games define `main`, `mgInit`, `MainLoop` and the other PS2 names (`chronicletwo:port/src/main.cpp:332`; `port/CMakeLists.txt`). Linking both into one executable needs renaming or namespacing, which is a large mechanical change to the `ps2/src` build (inference from the override mechanism).
- **The renderer cannot be instantiated twice.** `RendererInit` replaces the global `Context` (`renderer.cpp:795-799`), and `renderer_instance` only guards stale display lists against a new instance (`renderer.cpp:795`, `displaylist.cpp:931`, `:1507`). Making the renderer an instance would touch `renderer.cpp`, `resources.cpp`, `displaylist.cpp` and `draw.cpp` (inference from the file layout).
- **Blocking main loops.** `MainLoop` is a monolithic `while (1)` that never yields (`mainloop.cpp:73`, `:204`). Running two games means either re-entering each loop from a scheduler (a refactor of the loop into resumable state), or running each on its own thread with the global state split. The `sce` thread emulation and `RotateThreadReadyQueue` (`mglib_time.cpp`) are part of this and were not read in depth.
- **Logical size is fixed.** DC1's 640x480 and DC2's 512x480 cannot both be the renderer's logical frame (`renderer.cpp:794-828`; no setter). A switch between them would otherwise be a full renderer restart: `RendererShutdown` and `RendererInit`, which drops all textures, meshes and targets (`renderer.cpp:830-880`). Rendering each game into its own logical-size target and compositing is the alternative (inference; not checked for aspect or cost).
- **Canonical and previous-frame coupling.** Both games' canonical renders would alternate in one renderer, so `kPreviousFrame` (used by ChronicleTwo's menu grab and effects, `menudraw.cpp:128-137`, `effectlist.cpp:21`) would hold the other game's frame unless each game's canonical render follows its own previous one. Display renders are refused when the newest main image is not canonical (`gfx.hpp`). A switch that presents a game's display list after the other game ticked would fail or show the wrong previous frame (inference from the documented rules).
- **Named-target collisions.** A name used by both games at different sizes destroys the other game's handle (`resources.cpp:602-622`). This would appear as a missing or black effect, not as an error.
- **Shared frame pacing.** The game's wait inside `mgEndFrame` (`mglib.cpp:1354`) is the only place display frames are paced. A host would have to own that wait, or the two games' waits would interleave with the single clock tick callback (`clock.cpp:107`; `mglib.cpp:1147`; `main.cpp:307`).
- **Event and input pumping inside presentation.** `present.cpp:51-57` pumps window events and input. A second pump, or a pump from the wrong game, would double-consume input and events.
- **Mouse-look state is consumed on read.** `MouseFixedActive` takes the mouse sample delta and sets `before = sample` on every call (`camera_fixed.cpp:225-250`). It is called from several places in a present cycle (`present.cpp:127`, `:197`, `:291`; `camera_fixed.cpp:255`). Whether a second game's presenter would see a changed look is not verified here.
- **Settings reconciliation.** Window size, fullscreen, present mode, aspect and UI scale come from one config file per game (`identity.cpp:7-10`; `docs/PC.md`, "config.json"). A visible-game switch would have to choose one authoritative set and reapply it through `DisplayApply` (`platform/display.hpp`; `options/screen.cpp:49`).
- **Two windows is a different design.** Keeping one window per game and showing one at a time avoids most of the singleton problems, at the cost of two devices and two windows. Display lists are tied to their renderer (`renderer_instance`), so lists cannot cross processes; only pixels could (inference).
- **First-run setup window.** A windowed run opens a separate desktop setup window before the game window when data is missing (`docs/PC.md`, "Game data and first run"). A combined host would have to decide where that happens.
- **Exit paths.** `--frames` exits through `std::exit` in `mgEndFrame` (`mglib.cpp:1351`) and window close exits in `PumpHost` (`main.cpp:215-218`). A host would have to replace both.
- **Texture and mesh budget.** Texture slots are 8192 across the renderer (`context.hpp`); both games' assets would share them. Destruction is deferred until the GPU is done (`gfx README`, "Lifecycle"), so the cost of unloading a world is paid later, not at the switch.

## Open questions

- Should Ixion pin one Kazarov revision for both games? Chronicle uses the older layout (`a0a5ff8`, headers under `port/gfx`), ChronicleTwo uses `3dc38ce`. The API surface is nearly identical apart from `SetInterp2D`. Which one is canonical for a shared build is a decision, not a fact.
- Could `kPreviousFrame` be made per game? Would that need the host to keep a separate canonical image per game, and does the renderer allow it without the blit cost?
- How does the presenter's `MouseFixedActive` behave when called more than once per present cycle? A read of `camera_fixed.cpp:225-260` and a test would settle it.
- Does either game's `sce` thread emulation (`sce/threads`, `RotateThreadReadyQueue`) require its own stack or thread, and could two MainLoops share one? Not read in depth.
- Is the logical 512x480 frame on a 4:3 display visually correct for DC2 today? The per-axis stretch noted above is an inference from the README rule and should be checked against a screenshot.
- Is there a cost measurement for rendering both games' frames at their own logical sizes and compositing? Not measured here.
