# ChronicleTwo memory model and global state

## What this covers

How the ChronicleTwo (Dark Chronicle, DC2) PC port keeps the PS2's memory model: the quadword `mgCMemory` managers, the retail statics that become Kazarov arena roots, the main-arena reclaim points at loop entry, the monster script-stack slots, the renderer buffer pools, the save-data singleton and its raw dump, and the file-scope globals that hold game state. It then lists what would have to be isolated, namespaced or reset if the Chronicle (DC1) port and this port share one process. It also says what `docs/BSS_RESERVATIONS.md` and `docs/DATA_LAYOUT.md` do and do not establish about runtime layout.

Snapshot: ixion branch at 40ec9083 (ChronicleTwo master f44a756), Kazarov submodule pinned at 3dc38ce. Chronicle compared at master 3bc16763, Kazarov pinned at a0a5ff8. Counts below come from grep passes over the trees and are approximate unless a line is cited.

## Key facts

- The arena layer is one shared allocator. `ArenaBlock(owner, bytes, lead)` returns a zeroed, 64-byte aligned block kept for an owner key, with a guard page after it (kazarov:src/cpp/platform/arena.cpp:50-67, header at kazarov:include/platform/arena.hpp:18). The implementation is byte-identical between the two Kazarov pins (at a0a5ff8 the file is `port/platform/arena.cpp`, at 3dc38ce it is `src/cpp/platform/arena.cpp`; the two blobs compare equal).
- Headroom is 4x. `kArenaHeadroom = 4` (kazarov:include/platform/arena.hpp:11). Every port root multiplies the retail quadword count by it (chronicletwo:port/src/arena_root.cpp:13; chronicletwo:port/src/mg_memory.cpp:228, 371).
- An owner that outgrows its block gets a new zeroed mapping and the old block is zeroed and moved to a list that is never unmapped (kazarov:src/cpp/platform/arena.cpp:55-62, 16-19). Asking for more than the current capacity wipes live contents rather than copying them.
- `ArenaRoot(key, quads, name)` is the port's wrapper. The key is the retail buffer's address, so each retail static gets its own block. The first call logs one line per block (chronicletwo:port/src/arena_root.cpp:12-27).
- `ArenaRootFromBuffer` copies the retail bytes into the root only on the first import for that root. Later rebinds keep the live contents (chronicletwo:port/src/arena_root.cpp:29-40).
- The DC2 main arena is one retail static, `u_long128 main_buffer[0x1A0000]` (chronicletwo:ps2/src/mainloop.cpp:87). The port roots it as `MainBuffer` with 0x1A0000 quadwords (chronicletwo:port/src/mainloop.cpp:84) and gives the stack manager the 4x size (port mainloop.cpp:87). That is 27,262,976 retail bytes and 109,051,904 host bytes (about 104 MiB).
- `GetMainStack()` returns the address of one file-scope `mgCMemory` (chronicletwo:ps2/src/mainloop.cpp:345-347; object at 2141, `static`). Eleven `ps2/src` call sites in seven units call it (convviewlp, dng_main, editloop, mainloop, mainloop3, movieviewlp, title).
- Other fixed roots in the loop: `InfoStack` over `PortInfoBuff` (5000 quadwords, 320,000 host bytes, port mainloop.cpp:140), `SystemSeStack` over `PortSystemSeBuff` (400 quadwords, 25,600 host bytes, port mainloop.cpp:158), and `ItemMessages` over a file-local `char message_root` (chronicletwo:port/src/gamedata.cpp:18-25, 0x280 quadwords).
- Reclaim points that invalidate main-arena contents on loop entry:
  - Title and "omake" entry resets the main stack and re-points the sub-game save alias at the start of the arena (chronicletwo:port/src/mainloop.cpp:205-208).
  - `EditInit` (town and Georama editor) sets `main_stack->stack_used = 0` and re-carves the arena (chronicletwo:ps2/src/editloop.cpp:548, 590-606).
  - `InitDungeonMain` calls `memoryInit`, which calls `MainBuffer->stReset()` and re-carves every dungeon buffer (chronicletwo:ps2/src/dng_main.cpp:259-265, 325-327).
  - `LanguageChange` reloads `InfoStack` from its start (chronicletwo:ps2/src/mainloop.cpp:455-456).
- The loop state machine is process-global. `LoopInit[PortLoopNo]` runs once per entry (chronicletwo:port/src/mainloop.cpp:259), the inner loop runs, then `LoopExit[PortLoopNo]()` and `MemoryLogPeaks()` (port mainloop.cpp:395-396), then `PortLoopNo = PortNextLoopNo` (port mainloop.cpp:408). Ten modes exist (chronicletwo:ps2/include/mainloop.hpp:32-42); the dispatch tables are at chronicletwo:ps2/src/mainloop.cpp:100-110.
- A stack manager is a 0x30-byte class on PS2 (chronicletwo:ps2/include/mg_memory.hpp:44-60, size asserted at 245). `mgMEMORY_BLOCK` is 0x10 on PS2 (mg_memory.hpp:29-36). Those asserts are no-ops on the host (chronicletwo:port/include/port.h:36-37). The port comment gives a host header as 24 bytes (chronicletwo:port/src/mg_memory.cpp:18-20). Inference: host `mgCMemory` is about 0x48 bytes (two 8-byte pointers replace two 4-byte ones), not 0x30.
- Placement `new` does not know about the object size. `operator new(size, u_long128*)` and `operator new[]` grow the most recent run in the arena by the host size of the object, using a file-scope `g_last_run` (chronicletwo:port/src/mg_memory.cpp:30-38, 160-184, 381-389).
- Overflow aborts instead of returning NULL. `AllocQuadwords` and `GrowLastRun` call `Overflow`, which calls `ArenaOverflow` (port mg_memory.cpp:130-158, 160-184; kazarov:src/cpp/platform/arena.cpp:100-108). Retail printed and returned NULL. `Free` of an unknown pointer aborts; retail spun forever (port mg_memory.cpp:268-272; retail ps2/src/mg_memory.cpp:88-89).
- Peak accounting is global. `PeakTable()` is a function-local `std::vector` of `{memory address, capacity, peak, name copy}` (port mg_memory.cpp:64-77). Entries outlive their managers and are removed only by `MemoryForget` (port mg_memory.cpp:408-417).
- The scene owns a stack array of 12 managers and a `stack_num`, with `stack_no` set by `AssignStack` (chronicletwo:ps2/include/scenesnd.hpp:336-339). Retail `CScene::ClearStack` walked the array with a 4-byte pointer stride. The port replaces it with an index walk (chronicletwo:port/src/scene.cpp:8-23; retail at chronicletwo:ps2/src/scene.cpp:893-913).
- Monster script stacks are child views. `CMonsterMan::memory[MONSTER_ACTIVE_MAX]` (chronicletwo:ps2/include/monster.hpp:420; `MONSTER_ACTIVE_MAX = 24` at monster.hpp:32). `PrepareMonsterMemory` carves each slot from scene stack 3 with `stAlloc64` and gives 4000 plus an extra quadword count for the wider script entries (chronicletwo:port/src/dng_event.cpp:16-25). The 4x headroom comes from the parent arena, not from this function.
- Renderer pools are file-scope `mgCMemory` objects in mglib: `static mgCMemory packet_buf[2]` and `data_buf[2]` (chronicletwo:ps2/src/mglib.cpp:31, 38). `mgSetPacketBuffer` copies the managers by value (mglib.cpp:582-589). `mgSetDataBuffer` re-carves `data_buf` from the pool's free space (mglib.cpp:591-600). Both are called again at each loop entry (chronicletwo:ps2/src/dng_main.cpp:273, 278; chronicletwo:ps2/src/editloop.cpp:474-475, 502, 506, 596).
- Save data is one large object. `CSaveData` is 0x65930 bytes on PS2 (chronicletwo:ps2/include/savedata.hpp:504), held by a file-scope `CSaveData SaveData` (chronicletwo:ps2/src/mainloop.cpp:2157). Access goes through `ActiveSaveData` (mainloop.cpp:218) and `GetSaveData()` (mainloop.cpp:329-331). The memory-card path copies `sizeof(CSaveData)` bytes and computes check digits over them (chronicletwo:ps2/src/memcard.cpp:1078-1083; restore at 1332-1333).
- `CSaveData` is not pinned on the host. `PORT_RECORD_ASSERT` pins several record types (for example `CSubGameData` at savedata.hpp:809 and `CSaveDataDungeon` at savedatadungeon.hpp:105), but `CSaveData` itself has none. Records keep the disc layout on the PC, but `CSaveData` is covered only by the `STATIC_ASSERT` at savedata.hpp:504, which is a no-op on the host (port.h:36-37).
- File-scope globals are numerous. A regex pass over `ps2/src` finds about 410 non-const, non-static variable definitions. The densest units are `dng_main.cpp` (about 78), `mglib.cpp` (about 44), `menusys.cpp` (about 32), `event_func.cpp` (about 29), `menumain.cpp` (about 27), `editloop.cpp` (about 26) and `mainloop.cpp` (about 23). About 66 file-scope non-static `mgCMemory` objects and 6 pointers exist, plus about 65 `static` ones.
- Singletons that hold a whole world's state include `MainScene` (mainloop.cpp:2145), `GameItemDataManage` (gamedata.cpp:476), `GamePad__2`, `PadCtrl`, `Font`, `CSnd`, `InitArg`, `DebugInfo`, `SystemMesStack`, the dungeon globals in `dng_main.cpp:116-134` (`DngSaveData`, `DngSaveDataDungeon`, `DngMainScene`, `ActiveMonster`, `MainChara__2`, `FxScriptMan`, `TreasureBoxMan`), and `EventObjHandleMother`, `EventRain`, `EventMarker` in `event_func.cpp:21832-21842`.
- Retail absolute addresses in `ps2/src` are mostly behind overrides. `StoreImage` (which writes to 0x2100000 at `ps2/src/mglib.cpp:1975-1991`) is replaced (chronicletwo:port/src/mglib.cpp:1413; the generated override list for `mglib.cpp` names it, unverified). The scratchpad address (0x70000000, `ps2/src/mg_visual.cpp:102`) is reached only through `GetScrPad`, which is replaced with `PS2_UNIMPLEMENTED()` (chronicletwo:port/src/mg_visual.cpp:253-255). The address-alias `| 0x20000000` expressions sit inside the retail `mgCVisualMDT::CreatePacket` body (`ps2/src/mg_visual.cpp:689, 703, 720`, with the function at line 668), and that entry point is replaced (`port/src/mg_visual.cpp:564`; the other `CreatePacket` overrides are at `port/src/mg_visual.cpp:573` and `port/src/mg_shadow.cpp:80`).
- Movie DMA helpers that write PS2 registers are not replaced. `viBufCreate`, `viBufReset`, `setD4_CHCR`, `videoDecMain` and `GetTagProgSize` remain compiled from `ps2/src/movie.cpp` (writes to 0x1000B4xx and 0x1000E0xx at movie.cpp:226-227, 770-829). Only the `CMovie` entry points are overridden (port/src/movie.cpp:139-205; the port_overrides.txt:74-79 citation is unverified). Their callers are the retail movie code.
- Truncation status, from the generated table: 47 rows, 36 replaced and 11 open. The open round trips are two in `ps2/src/movie.cpp` (chronicletwo:docs/port/truncations.md, Counts section).
- The shape of Chronicle (DC1) memory is different. It uses `CDataAlloc2` arenas over `GlobalDataBuffer` (chronicle:ps2/src/dataset.cpp:41), with `kGlobalQuads = 1690000` and a 4x host block (chronicle:port/src/dataalloc2_1.cpp:12, 17). That is 108,160,000 host bytes (about 103 MiB). Both ports therefore reserve about 207 MiB for their main arenas alone, before roots, statics and textures (inference from the constants; not measured).
- On Windows, `ArenaMemoryMap` uses `MEM_RESERVE | MEM_COMMIT` for the whole mapping, so the commit charge covers every arena's full capacity at map time (kazarov:src/cpp/platform/memory.cpp:25-32, 49-69). On Linux, the same mapping is `MAP_NORESERVE` and zeroed with `madvise(MADV_DONTNEED)` (memory.cpp:17-21, 71-78).
- The Windows image is linked above 4 GiB with `--dynamicbase --high-entropy-va` (chronicletwo:port/cmake/arena.cmake:4), so a truncated pointer faults. A debug build aborts if no arena block lies above 4 GiB (kazarov:src/cpp/platform/arena.cpp:37-46, 80-90).
- `ArenaClearAll()` zeroes every block in the process (kazarov:src/cpp/platform/arena.cpp:69-73). No caller remains in the port or `ps2/src`; only the Kazarov test calls it. Chronicle's port does call it, from `InitializeDataBuffer` and `BufferAllClear` (chronicle:port/src/dataset.cpp:37, 55).
- `BSS_RESERVATIONS.md` is about matching the PS2 ELF's BSS placement for the decompilation (chronicletwo:docs/BSS_RESERVATIONS.md:1-11, 64-82). It classifies 155 BSS gaps and lists 153 retail placements in `postprocess_object.py` (the 155 and 153 counts match `docs/BSS_RESERVATIONS.md` lines 3-4; the `postprocess_object.py` list itself was not opened). It establishes nothing about runtime memory. `DATA_LAYOUT.md` is the same kind of document, for splitter and objdiff data identity (chronicletwo:docs/DATA_LAYOUT.md:1-9, 68-86). Neither says anything about arena behaviour on the PC.
- Name collisions across the two ports, found by a grep pass and confirmed by reading both sides:
  - Non-static globals with the same name and different types: `read_buffer` (`u_long128 *` at chronicletwo:ps2/src/mainloop.cpp:2110; `u_int *` at chronicle:ps2/src/dataset.cpp:30), `WorkBuffer` (`mgCMemory` at chronicletwo:ps2/src/editloop.cpp:3145; `CDataAlloc2<1> *` at chronicle:ps2/src/dataset.cpp:31), `SaveData` (object at chronicletwo:mainloop.cpp:2157; pointer at chronicle:ps2/src/main.cpp:119), `CSnd` (chronicletwo:mainloop.cpp:2117; chronicle:ps2/src/main.cpp:136), `LanguageCode` (chronicletwo:mainloop.cpp:2114; chronicle:ps2/src/mainselect.cpp:9, 11), `mgRenderInfo` (chronicletwo:ps2/src/mglib.cpp:22 as `mgRENDER_INFO`; chronicle:ps2/src/mglib.cpp:77 as `RenderInfo`), `mgDBuff` (mglib.cpp:2051; chronicle:mglib.cpp:54), `gs_simage` (mglib.cpp:2053; chronicle:mglib.cpp:89), and `DmaCH1` (mglib.cpp:2015; chronicle:mglib.cpp:28).
  - Shared class names with different layouts: `CSaveData` (chronicletwo:savedata.hpp:504 asserts 0x65930; chronicle:ps2/include/savedata.hpp:501 asserts 78272); `CGamePad` (chronicletwo:ps2/include/gamepad.hpp:676 asserts 0x478; chronicle:ps2/include/gamepad.hpp:451 asserts 0x468); `ClsMes` (chronicletwo:ps2/include/nd_meswin.hpp:1066 asserts 0x2958; chronicle:ps2/include/clsmes.hpp:593 asserts 0x1858 under PAL and 595 asserts 0x17B8 otherwise). The grep pass finds 49 shared type names in total, including `CSound`, `CMap`, `CObject`, `RS_STACKDATA` and `RS_CALLDATA`.
  - Duplicate `PORT_OVERRIDE` definitions (34 shared names by grep): placement `operator new` (chronicletwo:port/src/mg_memory.cpp:381-389 and chronicle:port/src/dataalloc2_1.cpp:55-61, each with its own last-run state), `LoadFile` and `LoadFile2` (chronicletwo:port/src/dataread.cpp:499, 507; chronicle:port/src/dataread.cpp:155, 164), `CGamePad::On`, `Down` and others, `CSound::Init`, `CSound::SE_Play` and others, `ezMidi`, `ezMidiInit`, `set_spu`, `WriteFile`, `InitCDFile`, and `main`.
- Retail `MainBuffer` has two declarations in one file: `extern mgCMemory MainBuffer;` (chronicletwo:ps2/src/mainloop.cpp:203) and `static mgCMemory MainBuffer;` (mainloop.cpp:2141). `dng_main.cpp:76` defines an unrelated file-scope `mgCMemory *MainBuffer`. The PC build tree holds object files for both the port and ps2 `mainloop.cpp`, so the toolchain accepted the file. Reason not checked (unverified).

## How it works

Boot, in `MainLoop` (chronicletwo:port/src/mainloop.cpp:81 onward):

1. The main arena is rooted once. `ArenaRoot(&main_buffer, 0x1A0000, "MainBuffer")` returns a block of 4x size, and `GetMainStack()->stSetBuffer(block, 0x1A0000 * 4)` binds the stack manager to it (port mainloop.cpp:84-88).
2. The rest of the statics that the port relocates are rooted the same way: `InfoStack` (line 140), `SystemSeStack` (line 158), and the item-message root through `CGameData::LoadItemSystemMes` (port/src/gamedata.cpp:21-30).
3. `InitSaveData()` zeroes the one `CSaveData` (ps2/src/savedata.cpp:21 memsets `this`).
4. The loop runs. For each entry, `LoopInit` re-carves the main arena (title or omake: lines 205-208; editor: `EditInit`; dungeon: `memoryInit`). The mode runs, then `LoopExit`, then `MemoryLogPeaks` prints each arena's peak.

Arena lifecycle, from the `mgCMemory` side:

- Root: `stSetBuffer(retail_static, n)` where the static is not inside any block. `ArenaRootFromBuffer` roots it and copies the retail bytes once (port mg_memory.cpp:365-379; arena_root.cpp:29-40).
- Child view: a buffer already inside a block is used in place, with no copy and no new block (`ArenaContains`, arena.cpp:75-78). Almost all `stAlloc64`/`Alloc` results take this path, which is how a parent's headroom reaches children.
- Heap: `SetHeapMem` copies the retail bytes on every call whose buffer is not inside a block (port mg_memory.cpp:223-226). The production callers all pass child views (dng_main.cpp:303, editloop.cpp:714, editmap.cpp:356, event_func.cpp:18939, pbuggy.cpp:419), so the copy path is not exercised by them.
- Reset: `stReset`, `stack_used = 0`, `CScene::ClearStack` (port scene.cpp:8-23), and `stSetBuffer(NULL, 0)` for a deeper stack. None of these zeroes memory; they only move the cursor. Stale bytes stay until overwritten.
- Growth: `Alloc` past the end aborts (port mg_memory.cpp:141-158). A placement `new` into the last run grows that run (mg_memory.cpp:160-184).
- Accounting: `NotePeak` updates the entry in `PeakTable` on each allocation and on stack alignment (mg_memory.cpp:116-128, 186-203). `MemoryLogPeaks` prints the peaks at loop exit.

Owner-keyed blocks: `ArenaBlock(this, ...)` (chronicletwo:port/src/inventmn.cpp:80, owner is `CInventDataManage`) returns the existing block without zeroing when it fits. A new object at the same address inherits the old bytes.

## Ixion hooks

- Per-world main arena. Replace the single `GetMainStack()` (ps2/src/mainloop.cpp:345-347) with a lookup keyed by the active world, and give each world its own retail-static key for `ArenaRoot` (port/src/mainloop.cpp:84). Do not use `ArenaClearAll` as a world reset. The `ps2/src` callers of `GetMainStack` (eleven call sites in seven units) are the places to audit.
- Transition seam. The loop-entry call at chronicletwo:port/src/mainloop.cpp:259 and the exit call at line 395 are the one place every mode change passes through. Copy-out of the travelling party or save fields belongs before the `LoopExit` call; copy-in belongs after `LoopInit`. Reclaim already happens inside `EditInit` and `memoryInit`, so any cross-world data must sit outside `MainBuffer` or be copied out first.
- Save separation. `GetSaveData()` (ps2/src/mainloop.cpp:329) and the raw `memcpy` of `sizeof(CSaveData)` (memcard.cpp:1078, 1332) are the two places to keep Ixion's data out of the Chronicle save. A second save object with its own container format avoids the host-layout question entirely.
- Link-level isolation. The port already renames symbols with `asm("...")` labels (chronicletwo:port/src/mainloop_port.hpp:11-21). Extending that convention to every name that collides with the Chronicle side (the list above), or compiling each game as a separate static library with hidden visibility, removes the duplicate-symbol and ODR problems at link time. The `PORT_OVERRIDE` mechanism (chronicletwo:port/CMakeLists.txt, `port_override_defines` and the `unit_copy` step) keys replacements by name, so the same mechanism would need a per-game prefix.
- One placement `new`. Both ports define `operator new(size_t, u_long128*)`. Ixion needs exactly one definition, and a per-arena last-run record instead of a file-scope `g_last_run` (port mg_memory.cpp:38) if both worlds allocate in one process.
- Renderer pools. After any world switch, call `mgSetPacketBuffer` and `mgSetDataBuffer` again with the new world's managers, as `memoryInit` and `EditInit` already do (dng_main.cpp:273-278; editloop.cpp:474-506, 596). Their state is process-global (mglib.cpp:31-38).
- Monster-style child slots. `PrepareMonsterMemory` (port dng_event.cpp:16-25) is the pattern for a world-scoped child arena that is carved from a parent and reset with `ClearStack`.
- Budget. Use `MemoryLogPeaks` (port mainloop.cpp:396) and `MemoryUsage` (port/src/mg_memory_port.hpp:14) on a merged run to measure real peaks before choosing reservations. On Windows, the reserve-only mapping (kazarov:src/cpp/platform/memory.cpp:27 would have to be changed) would avoid committing the full 4x capacity at map time; that change is in the shared Kazarov submodule and would need agreement.
- Tests. `port/src/tests/arena_test.cpp`, `mg_memory_test.cpp` and `monster_memory_test.cpp` (line 15) cover the single-world paths. A two-world test that roots two statics, reclaims one, and checks the other is untouched would be the first regression check.

## Risks and blockers

- Name and type collisions are hard link or undefined-behaviour failures, not warnings. The list in Key facts (read_buffer, WorkBuffer, SaveData, CSnd, LanguageCode, mgRenderInfo, and others) and the duplicate `PORT_OVERRIDE` definitions (`operator new`, `LoadFile`, `LoadFile2`, `CGamePad::*`, `CSound::*`, `main`) block a single link.
- Class layout conflicts are ODR violations. `CGamePad`, `CSaveData` and `ClsMes` differ in size between the two games. Inline member functions and vtables with the same mangled names would be merged by the linker.
- Loop entry reclaims the main arena (editloop.cpp:590; dng_main.cpp:265). Anything a traveller needs must be copied out before the reclaim, or the copy is overwritten silently. No error is raised; stale bytes stay until overwritten.
- Owner-keyed `ArenaBlock` reuse (inventmn.cpp:80) and the grow-remap that zeroes live data (kazarov arena.cpp:58-62) mean an owner whose address is reused or that asks for more space loses its contents without an error.
- The `SetHeapMem` copy-on-every-call (mg_memory.cpp:223-226) differs from `stSetBuffer`, which copies once (arena_root.cpp:35-38). No production caller passes a raw static today, so this is latent. A future caller that does would wipe a live heap.
- Overflow is fatal on the PC (mg_memory.cpp:130-158). Retail returned NULL. A merged dataset that grows the same arena would abort rather than degrade, and the failure names the arena only if the manager has a name.
- Host struct growth. `mgCMemory` and `mgMEMORY_BLOCK` grow on the host (inference: about 0x48 and 0x18 bytes). Any code that assumes the PS2 stride is a bug. The `ClearStack` fix shows that such code exists (scene.cpp:8-23 comment).
- The save file is a raw dump of host `sizeof(CSaveData)` (memcard.cpp:1078-1083). Nothing on the PC pins that size (see Key facts). Adding fields to either save struct, or changing a nested type, silently changes the save format.
- Windows commit. Each arena commits its full 4x capacity at map time (memory.cpp:27). Two main arenas, about 207 MiB, plus roots and textures, is a real commit charge (inference).
- Retired blocks are never freed (arena.cpp:19, 59). Any loop that regrows an owner leaks the older mapping for the process lifetime.
- Movie DMA code (`viBufCreate`, `setD4_CHCR`, `videoDecMain`) writes to fixed PS2 addresses. It is compiled into the PC build and would fault if reached. Reachability was judged from the callers, which are retail movie functions behind replaced `CMovie` entry points, not from a run.
- The address-alias `| 0x20000000` and `& 0x0FFFFFFF` expressions are in replaced functions, so they are not a live hazard today. A merge that reintroduces the retail bodies of `CreatePacket` would reintroduce them.

## Open questions

- Does Ixion need both main arenas live at the same time, or is one world's data always discarded at a transition? The answer decides whether one arena can be shared or two are needed. Needs a trace of which loops read main-arena data across a loop change.
- What is the host `sizeof(CSaveData)` and `sizeof(mgCMemory)`? A one-line `static_assert` or `printf` at startup would settle it. Not measured here.
- Does any title-screen or loop-exit path keep pointers into `MainBuffer` across `LoopInit`? If so, the reclaim at editloop.cpp:590 or dng_main.cpp:265 is a use-after-reuse. Not traced.
- The two open round trips in `movie.cpp` (docs/port/truncations.md): are their functions reached from any replaced code?
- Why does `ps2/src/mainloop.cpp` declare `MainBuffer` both `extern` (line 203) and `static` (line 2142), and compile? Likely a compiler extension; not checked against the toolchain.
- Is `ArenaClearAll` intended for any post-boot reset? Chronicle's `BufferAllClear` calls it; the ChronicleTwo port does not. Confirm that absence is deliberate before any Ixion code reaches for it.
- The `mgSetDataBuffer` skip-header path advances `base` by 0x4000 bytes but reduces `size` by 0x800 quadwords (ps2/src/mglib.cpp:591-600). Units differ; this is retail code and may be correct, but a merge that changes pool sizes must check it.
