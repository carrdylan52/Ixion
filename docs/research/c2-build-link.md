# ChronicleTwo build and link model

## What this covers

How the ChronicleTwo (Dark Chronicle, DC2) PC port is configured, compiled and linked: the top-level and `port/` CMake files, the Kazarov CMake modules it includes, `port_override.py` and its unit copies, the stub headers, `linknames.cpp`, the executables, the test tree and the presets and build driver. It ends with what a shared-library build with a small C ABI and hidden game symbols would need, including static initialisation and the assumptions that the game is the main executable.

Source references: `chronicletwo:` is the ChronicleTwo tree at the `ixion` branch (base f44a756, the pinned Kazarov gitlink is 3dc38ce). `kazarov:` is Kazarov at the pin, read from the Kazarov main checkout (9310c53). The paths the port uses (`cmake/`, `src/cpp/`, `include/`, `scripts/build/`) are byte-identical between 3dc38ce and main, so the reading holds for both. `chronicle:` is Dark Cloud's tree, cited only where its link model differs. Line numbers are from the files as read; counts from grep are approximate and say so.

## Key facts

- The game is not built as a library. The three game object libraries `ct_ps2`, `ct_port` and `ct_host` are OBJECT libraries, and every executable pulls their objects in through `ct_link_game` (chronicletwo:port/CMakeLists.txt:150, 171, 196, 230-233). The tree has no SHARED or MODULE target for the game. The only INTERFACE library defined here is `ct_options`.
- `ct_link_game` lists the objects in the order `ct_port`, `ct_host`, `ct_ps2` (chronicletwo:port/CMakeLists.txt:231). Object files of one link are laid out in that order, so port-side globals are constructed before the PS2-side ones on the usual ELF and COFF linkers (inference, see Risks).
- PIC is forced on for all targets (chronicletwo:port/CMakeLists.txt:18). Language is C++26 with extensions off (lines 14-16). The compiler defaults to `clang++` when none is given (lines 9-11).
- Executables: `darkchronicle` (only `port/src/main.cpp` plus the game objects, lines 244-248), `darkchronicle_tests` (GoogleTest, `port/src/tests/main.cpp`, every `*_test.cpp`, linked with `ct_link_game` and `kz_port_tests`, chronicletwo:port/src/tests/CMakeLists.txt:20, 34-35), and `dc2data` plus `dc2data_bridge_test` from `tools/dc2data` (a Rust CLI over the extractor, chronicletwo:tools/dc2data/CMakeLists.txt).
- Host library: `kz_port_host_library(ct_host)` (chronicletwo:port/CMakeLists.txt:42) compiles Kazarov's `gfx`, `audio` and `platform` sources as one OBJECT library, builds GLSL shaders to SPIR-V headers with glslangValidator, and fetches vendored dr_libs and stb headers at pinned SHA-256 hashes when no vendor copy exists (kazarov:cmake/KazarovPort.cmake:34-111). `ct_host` is not linked to `ct_options`, so the host code is not compiled with `PORT`, `PAL` or `port.h` (kazarov:cmake/KazarovPort.cmake:1-5, the header comment: "Host code never sees a game header").
- The Kazarov SDK replacements (`kz_port_sce_sources`) are compiled into `ct_port` for libvu0, libpad, libmc, sifdev, sifrpc, eekernel, libcdvd, libgraph, libdma, libpkt, eekernel_threads, libdev, libmpeg, libsdr, modmsin and sifdma, plus `sce/unimplemented.cpp` (chronicletwo:port/CMakeLists.txt:194-196; kazarov:cmake/KazarovPort.cmake:113-130). Each family comes from `src/cpp/sce/<lib>.cpp` or `src/cpp/sce/stubs/<lib>.cpp`.
- PS2 units: 149 `.cpp` files under `ps2/src` (chronicletwo:port/CMakeLists.txt:78-82, which drops any `tmp*` scratch name; none exist today). Each one is built from a per-unit copy, not from the original file (foreach at line 110; copy rule at 122).
- The per-unit copy is produced by `scripts/port/unit_copy.py` with `--port-override` and `--overrides`, optionally `--stubs port/include/stubs/<unit>.hpp`, `--define=PORT`, `--define=PAL` and `--long-is-64` (chronicletwo:port/CMakeLists.txt:86, 110-134; chronicletwo:scripts/port/unit_copy.py:1-20). The stub header is force-included into the copy with `-include` (lines 129-132).
- `port_override.py` is Kazarov's tool. `list` collects the names tagged `PORT_OVERRIDE` in `port/src`; `strip` removes the matching definitions from a ps2 unit copy and keeps a declaration; `check` fails when a tag names no ps2 definition (kazarov:scripts/build/port_override.py:664; the check rule is chronicletwo:port/CMakeLists.txt:136-145).
- Matching is by signature, not by link name. A tagged definition is keyed as `Name(param,types)` with `long` and `long long` canonicalised (kazarov:scripts/build/port_override.py:231-236), so overloads need matching parameter types. `main` and `extern "C"` names are keyed by their bare name (port_override.py:303).
- `PORT_OVERRIDE` is defined as nothing in `port.h` (kazarov:include/kazarov/port.h:20 at the pin). About 320 lines in `port/src` `.cpp` files carry the tag (grep count, including a few in tests and comments); 83 `.cpp` and `.hpp` files in total.
- `port.h` is force-included into every game-side translation unit via `SHELL:-include` on `ct_options` (chronicletwo:port/CMakeLists.txt:155-157). The `PORT` and `PAL` macros are defined on the same interface (line 86, 150-151).
- Stub headers: 25 files in `port/include/stubs/`. They carry declarations and `#define` renames that `port_override.py` reads (`rename_map`, kazarov:scripts/build/port_override.py:492-499). Example: `#define Exit__2 Exit` (chronicletwo:port/include/stubs/mglib.hpp:4; also dataread.hpp:4).
- The 25 stub headers are named after the unit they serve: `collision`, `dataread`, `dng_main`, `dngmenu`, `editctrl`, `editloop`, `editmap2`, `event`, `event_func`, `gamedata`, `gamepad`, `gameutil`, `inventmn`, `mainloop`, `menuchr`, `menudraw`, `menumain`, `menuop`, `menusys`, `mg_frame`, `mg_math`, `mglib`, `nowload`, `photo`, `title` (chronicletwo:port/include/stubs/). A stub is included ahead of its unit only when it exists (chronicletwo:port/CMakeLists.txt:116-134).
- The same name `Exit__2` has two definitions in the tree: the PS2 SDK declaration (chronicletwo:ps2/include/sce/eekernel.h:147, 152) and the Kazarov shim `Exit` (kazarov:src/cpp/sce/eekernel.cpp:12-13). The stub renames (`#define Exit__2 Exit`) route game calls to the shim, and `exit__2` in `runtime.cpp:42` is a separate C-linkage definition that calls `std::exit`.
- The override check rejects static definitions: "a static definition replaces nothing in another unit" (kazarov:scripts/build/port_override.py:318-331, `tagged_names`). An override therefore has to be an external definition, and a file-local helper cannot be tagged.
- Kazarov's own GoogleTest cases (about 27 `*_test.cpp` under `src/cpp/tests`) are compiled into `darkchronicle_tests` by `kz_port_tests` (kazarov:cmake/KazarovPort.cmake:132-138), so the test binary also carries the shared gfx, audio and platform cases.
- Link-name labels: 107 `asm("...")` label uses in `port/src` and `port/include` (grep, tests excluded), covering 61 distinct labels (grep, tests excluded) such as `MainLoop_LoopNo` (chronicletwo:port/src/mainloop_port.hpp:12) and `DngMain_ResetEyeView` (chronicletwo:port/src/dungeon_eye.cpp:6). Retail-named globals and functions are reached through these labels. Chronicle's port has 14 distinct labels and none is shared with ChronicleTwo's set (grep, comm of the two sets).
- `RETAIL_BRIDGES` in `unit_copy.py` keeps two overridden retail routines under bridge names, for `editctrl.cpp` and `dng_main.cpp` (chronicletwo:scripts/port/unit_copy.py:41-43).
- `linknames.cpp` is 19 lines: placeholder arrays for the retired VU1 microcode (`My_dma_start0`, `Vu_progmain`, `Vu_prog0`, `Vu_prog_sdw`, `Vu_prog_3dsp`, `Vu_prog_wtr`) and `void *_gp = NULL;` (chronicletwo:port/src/linknames.cpp:8-19). No link alias or `--defsym` is used. Chronicle uses `--defsym` on ELF for its aliases (chronicle:port/CMakeLists.txt:209-210), and its CMake comment places the COFF aliases in `/alternatename` directives in its `linknames.cpp`.
- Link flags (chronicletwo:port/CMakeLists.txt:221-228):
  - Windows: `-fuse-ld=lld -Wl,--gc-sections -Wl,--error-limit=0 -Wl,--allow-multiple-definition`. The guard is documented as a tolerance for COMDAT copies that header fixups did not remove (lines 221-222).
  - Linux: `-fuse-ld=lld -pie -Wl,-z,separate-code -Wl,--gc-sections -Wl,--error-limit=0`.
  - macOS: `-Wl,-dead_strip`.
- Windows adds `-municode` to `darkchronicle` (line 248), `-Wl,--dynamicbase -Wl,--high-entropy-va` (chronicletwo:port/cmake/arena.cmake:4), and `-Xclang -mno-constructor-aliases` on every game object (line 162-164). The comment says constructor aliases would point into a COMDAT section that lld discards under `--allow-multiple-definition`.
- Libraries that the executables link (chronicletwo:port/CMakeLists.txt:233, 240): `ct_options`, `kz_port_headers`, `SDL3::SDL3`, `Vulkan::Vulkan`, `kazarov_bridge`, `kazarov_core`, and on Windows `imm32 uxtheme opengl32 dwmapi`.
- `kazarov_core` is the Rust crate with `crate-type = ["staticlib", "rlib"]` (kazarov:Cargo.toml:9). Corrosion imports it and builds `kazarov_bridge` (the cxx bridge) (kazarov:cmake/KazarovRust.cmake:20-21). Both are static, so each game executable carries its own Rust runtime and bridge.
- FFmpeg: `kz_ffmpeg(ct_options INTERFACE)` attaches the LGPL MPEG-2 decoder to every game link (chronicletwo:port/cmake/movies.cmake:1-5; kazarov:cmake/KazarovFfmpeg.cmake). On Linux it is static archives; on Windows it is the shared LGPL build's import libraries, with DLLs copied beside the executable.
- Windows runtime DLLs (SDL3, libc++, libwinpthread, libunwind, the Vulkan loader, FFmpeg's avcodec, avutil and swresample) are copied next to each executable by `kz_windows_runtime` (chronicletwo:port/CMakeLists.txt:265-270; kazarov:cmake/KazarovWindowsRuntime.cmake).
- Tests: about 123 `*_test.cpp` files with about 800 `TEST(` cases (grep). `gtest_discover_tests` runs each case in its own process because "the game's state is global" (chronicletwo:port/src/tests/CMakeLists.txt header and lines 102-119). Cases carry labels `gpu` or are CPU-only, with timeouts `CT_TEST_TIMEOUT` = 5 s and `CT_GPU_SLOW_TIMEOUT` = 30 s (lines 40-45). A smoke test runs `darkchronicle --headless --offscreen --frames 3 --screenshot` and checks the PNG signature (lines 151-160).
- The test binary links the same game objects, so tests see the same global symbol set as the executable (chronicletwo:port/src/tests/CMakeLists.txt:34).
- Presets: `CMakePresets.json` has hidden `pc` and `linux`/`macos` bases and concrete `linux-x64`, `linux-x64-release`, `macos-arm64` and `macos-arm64-release` presets, with binary dirs under `port/build/` (chronicletwo:CMakePresets.json). `build.sh` and `build.bat` delegate to `tools/kazarov/scripts/kazarov build` (chronicletwo:build.sh; chronicletwo:build.bat), using `kazarov.conf`'s configurations (chronicletwo:kazarov.conf:5, 10-11; the Windows config is `windows-x64-release`, Debug is `windows-x64`).
- Optional build switch `CT_DEBUG_OPT` (default OFF) adds `-Og` to the three game libraries in Debug (chronicletwo:port/CMakeLists.txt:210-216).
- The PC compile needs no disc. `ct_ps2` depends only on `ps2_include` and the override check, not on `rom/` (chronicletwo:port/CMakeLists.txt:171-174). Game data is extracted on first run (chronicletwo:docs/PC.md:24, 178).
- Startup: the port's `main` is `PORT_OVERRIDE int main(int, const char **)` (chronicletwo:port/src/main.cpp:332), with `wmain` on Windows (line 337) and the body in `Run` (lines 250-328). The PS2 `main()` in `ps2/src/main.cpp:138` is replaced by this, so `init()` and its `mwInit()` call are never reached in the port.
- `mwInit()` is empty on the host (chronicletwo:port/src/runtime.cpp:39-40). Static constructors run before `main` from the C runtime (chronicletwo:docs/PC.md:371).
- Process-exit call sites (about 30 in all, 14 of them in `ps2/src/runscript.cpp` including `runerror`'s; the ones in `test_hooks.cpp` are test-only; most are reachable in a PC run):
  - chronicletwo:port/src/main.cpp:91 (usage, status 2, reached from `ParseOptions`), 217 (`PumpHost` when the window closes), 268 (bad input script).
  - chronicletwo:port/src/mglib.cpp:1351 (`--frames` limit, from `mgEndFrame`).
  - chronicletwo:port/src/present.cpp:54 (window closed while polling in the overlay path).
  - chronicletwo:port/src/platform/firstrun.cpp:67 (no data, status 3).
  - chronicletwo:port/src/runtime.cpp:43 (`exit__2`, the game's `exit`) and 14 (`__assert` uses `_Exit`).
  - chronicletwo:port/src/test_hooks.cpp:38, 166, 229 (`exit(2)`).
  - kazarov:src/cpp/sce/eekernel.cpp:12-13 (`Exit` calls `std::exit`). Game callers reach it through `Exit__2` (chronicletwo:ps2/src/dataread.cpp:524, 678; ps2/src/mglib.cpp:938).
  - kazarov:src/cpp/platform/window.cpp:24 (`Fatal`), 166 (`SDL_Quit` in `WindowShutdown`).
  - kazarov:src/cpp/gfx/renderer.cpp:29 (`std::exit(1)`) and kazarov:src/cpp/platform/paths.cpp:166 (`std::exit(2)`).
  - chronicletwo:ps2/src/runscript.cpp:15-18 (`runerror` calls libc `exit(-1)`), with 13 `exit(` calls in that file besides `runerror`'s (for example 40, 179), and ps2/src/editdata.cpp:255 (`exit(0)`). The port overrides only `CRunScript::check_program` in `port/src/runscript.cpp:5`, so these stay.
  - Aborts (process-wide, not a clean exit): chronicletwo:port/src/menuchr.cpp:38, port/src/mg_memory.cpp:271, and Kazarov's `arena.cpp`, `memory.cpp`, `eekernel_threads.cpp` and `unimplemented.cpp:8`.
- The window-close path in the port is documented as the process end: "A closed window ends the process here: the game has no stop request to ask its loop to return" (chronicletwo:port/src/main.cpp:214).
- `MainLoop` is `PORT_OVERRIDE void MainLoop()` (chronicletwo:port/src/mainloop.cpp:73). Its outer `while (1)` starts at line 204. It leaves through `break` when `PortLoopNo` is out of range (lines 214-215), then runs cleanup and `GamePad__2.Close()` (line 427). Nested loops also `break`. So the function can return, but only on that path; every other exit is `std::exit` from the list above.
- Kazarov's clock is pull-driven: the game's own calls (`sceGsSyncV`, `WaitVSync`, `mgEndFrame`) call `ClockPump`, which runs the tick callback and the registered pump hooks (kazarov:include/platform/clock.hpp:24, 62, 68-71 at the pin). `ClockAddPumpHook(PumpHost)` is installed at chronicletwo:port/src/main.cpp:306.
- PS2 kernel threads are cooperative fibers on one OS thread: `ucontext` on Linux and Win32 fibers on Windows (chronicletwo:docs/PC.md:742). On Windows, `ContextInitMain` calls `ConvertThreadToFiber` and aborts when it fails (kazarov:src/cpp/sce/eekernel_threads.cpp:55-59 at the pin). A switch inside `ClockPump` is an abort (chronicletwo:docs/PC.md:744; kazarov:include/platform/clock.hpp:68-69).
- Process-wide Kazarov state that a second game in the same process would share or overwrite: `SDL_SetAppMetadata` and `SDL_Init` (window.cpp:62, 72), `SDL_Quit` (window.cpp:166), the settings environment prefix `g_env_prefix` (kazarov:src/cpp/platform/settings.cpp:8), and `GameSetIdentity()` which sets the `DC2` prefix, the `chronicletwo` app directory and the window title (chronicletwo:port/src/identity.cpp:7-11).
- The design says Ixion is "a launcher, a bundle format and a set of station rules, not a shared runtime" (chronicletwo:ixion/docs/DESIGN.md, section 1). A shared-library build would be the first in-process runtime step, so the decision is design-level as well as build-level.

## How it works

1. Configure. The top-level CMake sets C++26, PIC, and locates the Kazarov submodule (`tools/kazarov`), which must be initialised. It reads `data_version.json` and writes the data-version header into the build tree (top of chronicletwo:port/CMakeLists.txt). It includes `KazarovPort.cmake`, sets `KZ_PORT_BUILD_TIM2` OFF with FORCE (line 39), and calls `kz_port_host_library(ct_host)` (line 42). The mirror of `ps2/include` is produced by `scripts/port/header_fixups.py`, which rewrites `long` to `long long` and applies a fixed list of header edits (lines 45-75).
2. Override listing. `port_override.py list port/src` writes `port_overrides.txt`. Each PS2 unit gets a split file of its own overrides so an override edit recopies only the units it reaches (lines 100-134). Copies live in `build/ps2_src/`.
3. Override check. `port_override.py check` runs over the PS2 sources, the stub directory and the defines, and writes `port_overrides.checked`. A failing tag stops the build (lines 136-147; kazarov:scripts/build/port_override.py:664).
4. Object compile. `ct_ps2` compiles the 149 unit copies with `ct_options` and the MWCC-tolerance flags: `-ftrivial-auto-var-init=zero`, `-fno-strict-return`, `-fno-strict-aliasing`, `-fwrapv`, a long list of `-Wno-*` for MWCC-era code, and `-Wall` (lines 171-190). `ct_port` compiles `port/src` minus tests and `main.cpp` (lines 191-198). `ct_host` is Kazarov's.
5. Link. `ct_link_game` composes the objects, links the libraries and adds the platform flags (lines 230-242). Windows also copies runtime DLLs (lines 264-272). The Rust static archives and the cxx bridge are linked directly, so Rust code and the game objects share one image.
6. Runtime start. The C runtime runs constructors (`.init_array` on ELF, the CRT's `.CRT$XC*` sections on COFF). `main` (`port/src/main.cpp:332`) then calls `Run`, which sets identity, parses options, loads config, checks data, opens the window, starts the renderer and audio, installs the pump hook and the tick callback, indexes the data root (`InitCDFile`, `dataread.cpp`) and calls `MainLoop()` (`main.cpp:250-317`).
7. Override semantics at link. A tagged port definition exists only in `ct_port`. The PS2 copy keeps the declaration. A `check`-verified signature match is the only binding, so there is no link-time ambiguity for ordinary functions. The exceptions are duplicates that the Windows flag silently accepts (see Risks).
8. Tests use the same objects and the same override pipeline. Each test case is its own process. The smoke test drives the real executable headless.

## Ixion hooks

- `port/CMakeLists.txt`, next to `ct_link_game` (lines 230-242): add a `SHARED` (or `MODULE`) target built from `$<TARGET_OBJECTS:ct_port>`, `$<TARGET_OBJECTS:ct_host>` and `$<TARGET_OBJECTS:ct_ps2>`, without `add_executable`. Hidden visibility has to be set on the three object libraries, because object files carry their own flags: `CXX_VISIBILITY_PRESET hidden` and `VISIBILITY_INLINES_HIDDEN ON` on `ct_ps2` and `ct_port`, and on `ct_host` after line 42. That is safe for the executable and the tests, which do not need game exports. On ELF, add a version script that exports only `ixion_*`. On PE, mark only the entry points `__declspec(dllexport)`; COFF exports nothing else by default (inference, check that lld does not auto-export when any `dllexport` is present).
- New entry translation unit in `port/src` next to `main.cpp`. It exports a small `extern "C"` ABI, for example `ixion_game_create`, `ixion_game_pump`, `ixion_game_destroy`, and calls a refactored body of `Run` (`main.cpp:250-328`) that takes an options struct instead of argv. `Run` currently mutates argv through `PathsConsumeArgs` (line 252), calls `GameSetIdentity()` (line 251) and can `std::exit` through `Usage` (line 91, reached from `ParseOptions` at line 253) and at line 268 (bad input script). Those need an error return.
- Exit redirection. The seams, in order of preference: a link-time wrap for the libc and CRT calls, a `PORT_OVERRIDE` for each game-side function that exits, and a stub `#define` only for names the unit does not include headers for. Candidates:
  - `runtime.cpp:42-44` (`exit__2`) and the `Exit` shim (Kazarov's `eekernel.cpp:12-13`). The Kazarov one is compiled into `ct_port` from `kz_port_sce_sources`, so an Ixion-side definition of `Exit` would duplicate it. Either replace the SDK family for Ixion, or change the Kazarov source under the submodule rules.
  - `ps2/src/runscript.cpp` `runerror` and the other `exit(` sites (13 in that file, plus `editdata.cpp:255`, `dataread.cpp:524, 678`, `mglib.cpp:938`): a `#define exit` in a stub header is the obvious tool, but the stub is `-include`d before the unit, so it would also rewrite the unit's own `<cstdlib>` declarations (`ps2/src/runscript.cpp:5`; the `<cstdlib>` include is there). A link-time redirect is cleaner: `-Wl,--wrap=exit` (and `_Exit`, `abort` where wanted) sends every undefined reference from the game objects to `__wrap_exit`, with no source edit (inference: lld supports `--wrap` on ELF and COFF). Kazarov's calls go through the same wrap.
  - `main.cpp:217` `PumpHost`, `present.cpp:54` and `mglib.cpp:1351`: replace `std::exit` with a flag that the pump checks and that makes `MainLoop` return through the path at `mainloop.cpp:214-215`.
- Symbol hygiene for the internal C-linkage names: `srand`, `rand`, `exit__2`, `fptosi`, `fptoui`, `__assert`, `mwInit`, `__construct_new_array` (`runtime.cpp:30-74`) and the `_gp` and VU placeholder globals (`linknames.cpp`). On ELF with default visibility, a DSO's `rand` can be interposed by libc's for calls from the DSO itself (inference). Hidden visibility fixes that. The game depends on the exact sequence of its own generator (runtime.cpp:24-37).
- Static initialisation. Constructors run when the DSO is loaded, before the Ixion entry point is called. Keep them free of game API calls: `CFont()` calls `Init()` (`ps2/include/font.hpp:189`), `CPot()` calls `Init(0)` (`ps2/include/pot.hpp:224`), and `CWaveTable` declares a user constructor (`ps2/include/wavetable.hpp:44`). Examples of file-scope objects with constructors: `CCameraControl MainCamera` (`ps2/src/dng_main.cpp:199`), `CPullItemManager PullItemMan` (line 133), `static CFont dbFont` (`ps2/src/dng_debug.cpp:102`), `CWaveTable WaveTable` (`ps2/src/editloop.cpp:3138`). Port-side globals of std containers (`port/src/dataread.cpp:44`, `port/src/mglib.cpp:81-140`, `port/src/mglib_time.cpp:19`) are constructed in the same phase.
- Per-game identity. `GameSetIdentity`, `SettingsSetEnvPrefix`, `PathsConfigure` and `WindowSetIdentity` are process-global. Either keep one DSO per game (each gets its own copy of these) or parameterise them so both games can run in one process.
- Thread model. Fibers are created per OS thread (`ConvertThreadToFiber` in `eekernel_threads.cpp:55`). The Ixion host should run each game on one dedicated thread and call into it only from there. Ixion's own UI thread must not already be a fiber.
- Window and SDL ownership. `WindowShutdown` calls `SDL_Quit` (window.cpp:166), which would tear down the other game's SDL if both run in one process. Ixion needs one shared SDL owner, or a process per game.
- Passenger transfer. Save structs are plain data and are the most natural payload to pass across a DSO boundary: `SaveData.Initialize()` and `PortActiveSaveData`, set at the start of `MainLoop` (chronicletwo:port/src/mainloop.cpp:73 onward), are the existing seams. A bundle format built on the save structs keeps the link surface small. This is for the design topic, not the build.

## Risks and blockers

- Exit semantics. The game and Kazarov call process exit from about 30 sites (see Key facts), including `exit(-1)` from the script VM (`ps2/src/runscript.cpp:15-18`) and the window-close path. A DSO that does not change these terminates the host process. Some are reachable only in error paths, but the window-close and `--frames` paths are normal.
- Loop shape. `MainLoop` is a single blocking function that runs the whole game. Its only clean return is the out-of-range loop number (`mainloop.cpp:214-215`). A host that wants to step the game has to run it on its own thread or fiber, or convert `MainLoop` into a stepper, which is a large change.
- Symbol collisions between the two games. The two ps2 trees share 22 unit file names (among them `main.cpp`, `map.cpp`, `sound.cpp`, `water.cpp`, `character.cpp` and `runscript.cpp`) and 16 class names at column zero in headers (unverified count) (`CMap`, `CSound`, `CSaveData`, `CScriptInterpreter`, `CObject`, `CEffect`, `CWater`, `CGamePad`, `CRunScript`, `ClsMes` and others). Their layouts differ (not verified field by field). Linking both into one image would violate the ODR, and the Windows `--allow-multiple-definition` would hide the duplicate-symbol errors that other platforms print. Two DSOs with hidden visibility avoid this; one merged image needs namespaces or renaming first.
- Windows duplicate tolerance. `--allow-multiple-definition` (chronicletwo:port/CMakeLists.txt:223) means a duplicate definition in a merged build is not an error. Any merge needs a duplicate-symbol check on Linux or macOS, or a `lld` run without this flag.
- Shared process singletons. SDL (`SDL_Init`, `SDL_Quit`, `SDL_SetAppMetadata`), the Vulkan loader, the settings prefix and the identity globals are per process. Two DSOs load one `SDL3.dll` and one `vulkan-1.dll`, so their state is shared (inference from `window.cpp:62, 72, 166` and `settings.cpp:8`).
- Rust runtime. `kazarov_core` is a static Rust library with `eframe` and its windowing dependencies (kazarov:Cargo.toml). Two DSOs each carry a Rust runtime and a cxx bridge, so their exported symbols must stay hidden. Window-class registration by winit inside one process has not been checked (open question).
- Fiber thread affinity. The game's threads are fibers on one OS thread, created by `ConvertThreadToFiber` on first use. A DSO entered from a thread that is already a fiber would abort (`eekernel_threads.cpp:55-59`).
- Static-init order across objects. The link order (port, host, PS2) fixes the order within one link. Across DSOs there is no defined order, and a PS2 constructor that uses a port global whose constructor has not run is undefined behaviour. The current order works only by object order. The port already relies on this in one case: the constructors reach the SIF RPC layer before any client is bound, and the port answers those calls instead of aborting (chronicletwo:docs/PC.md:371).
- Teardown order. `atexit(AudioShutdown)` is registered in `Run` and `--frames` exits through `std::exit` "before the mixer's statics are destroyed" (`main.cpp:299-301`). A DSO unload runs its static destructors at a different point, so the audio and renderer teardown order changes.
- Build cost. Each game DSO needs its own `ct_host` copy (Kazarov's shared host code is compiled per consumer), so two games double the host and sce compile. Object reuse only applies within one configuration.
- Chronicle differs. The DC1 port uses the same object layout (`dc_host`, `dc_ps2`, `dc_port`, `darkcloud`) but adds `--defsym` and `/alternatename` aliases and no `--allow-multiple-definition` (chronicle:port/CMakeLists.txt:35, 103-122, 176, 203-210). A merged link would have to carry both sets of aliases.
- The DC2 build depends on Kazarov at 3dc38ce. Kazarov main has moved on elsewhere, but the paths this port uses (`cmake`, `src/cpp`, `include`, `scripts/build`) are unchanged between the pin and main. Any Kazarov bump has to re-check `KazarovPort.cmake` and `port_override.py`.

## Open questions

- Does `ConvertThreadToFiber` return the existing fiber, or fail, when the calling thread is already a fiber (`eekernel_threads.cpp:55-59`)? This decides whether Ixion's host thread can be a fiber itself.
- Does lld keep exported `ixion_*` symbols under `--gc-sections` when linking `-shared` or on COFF with `dllexport`? Verify with `llvm-readobj --coff-exports` or `--dynamic-table` on a test link.
- Does MinGW/UCRT run DLL constructors from `DllMain` attach for an lld-linked DLL, and in which order against the other DLLs? (inference: yes, through the CRT's `_CRT_INIT`)
- Which static constructors call into port or SDK code before `Run`? The PC.md note covers the RPC layer and `mgUnitMatrix`/`mgZeroMatrix`/`mgZeroVectorW` (docs/PC.md:371). A full list needs a constructor audit of the 149 units.
- Can `MainLoop` be driven as a stepper? The nested `while (1)` loops at `mainloop.cpp:204` and `:276` and the `sceGsSyncV` waits (`:416`) have to yield to a host, or the game has to run on its own thread.
- How many of the roughly 30 exit sites are reachable in normal play (title, town, dungeon, save, quit) versus only in debug or failure paths? This sets the minimum set of exit redirects.
- Is `rand` interposed on the target ELF toolchain for a DSO built with default visibility? A test link would answer it.
- Do the CMake `gtest_discover_tests` and `ctest` per-case isolation still hold if both games are in one test binary (they are not today)?
